## 已明确提出的需求

### 1. 探索 Live2D 形式的小窝

- 直接依据：金玉提出「用Live2d做小窝」。
- 需求含义：需要评估带动态角色的可视化表现，不只是追加账本表单或信息卡片。
- 尚未确定：Live2D 是否为硬性要求，还是希望达到类似的动态角色效果；模型、美术及动作资源由谁提供。

### 2. 改善「只有页面」的呈现

- 直接依据：「目前Diana后台小窝还是一些页面」。
- 整理归纳：让小窝具有角色所在空间的直观感，而不仅是管理入口。
- 边界：群里没有要求删除钱包、动态或原有页面，也没有明确提出独立客户端、公开访问或多人房间。

### 3. 用参考效果对齐预期

- 明确参考：Star-Office-UI 链接，以及金玉分享并再次引用的视频。
- 下一步：先核验视频，归纳哪些视觉和交互要保留，再做小型原型确认。
- 不能直接推出的需求：完整复刻参考项目、3D 场景、角色自由寻路、装修系统或全天候自主模拟。

### 对产品方向的修正

参考的重点不只是「Live2D 会动」，而是**角色在自己的房间里，通过位置、姿势、道具和灯光表达正在做什么**。聊天界面与房间画面并置，营造「她在那个房间里和我交流、处理事情」的感觉。

建议将最小原型从泛泛的待机立绘收敛为三个可演示状态：床上持手机、床与书桌之间的过渡、坐在电脑前。先用手动演示验证视觉，后续再接真实活动状态。这是依据画面提出的方案，不是群里已确认的动作清单。

### 尚不能由抽帧确认

- 是否真的使用 Live2D，或采用逐帧动画、视频片段及其他渲染技术。
- 从床到椅子的连续过渡是否流畅、是否支持自由移动或寻路。
- 动作由聊天指令、工具事件、时间规则还是人工控制触发。
- 短视频页面是否由角色实际打开，是否具备屏幕理解、音频理解能力。
- 语音、口型、音效、完整字幕，以及动作与回复之间的精确先后关系。

不能据此把屏幕监控、电脑接管、自由寻路或完整桌面宠物系统纳入已确认需求。

## 建议方案：先做能验证方向的最小原型

以下均为建议，尚未得到群内确认。

### 页面位置

继续放在现有「小窝」入口内，优先以场景作为展示区域，保留钱包与动态的原有访问路径；不另造一套脱离管理界面的导航。具体采用新增「房间」分档还是顶部场景区，等原型对比后决定。

### 第一阶段：视觉与交互原型

| 项目 | 建议内容 | 验证目的 |
| --- | --- | --- |
| 一个房间 | 一张背景、一个角色、少量明确区域 | 验证是否真正比静态后台更有「住在这里」的感觉 |
| 基础动态 | 参考抽帧设计床上持手机、床与书桌之间、坐在电脑前等状态；连续过渡待原视频补验 | 先证明视觉方向，不提前实现完整行为系统 |
| Live2D 可行性 | 使用授权清楚的测试模型验证加载、缩放、动作与移动端表现 | 确认资源条件和运行成本，而非先承诺特定 SDK 或渲染库 |
| 演示切换 | 用明确标注的演示状态展示不同表现 | 避免把假数据或演示动画当作机器人的真实活动 |
| 失败降级 | 模型缺失或渲染失败时显示静态形象，并继续允许访问原有功能 | 新视觉不能挡住账本和动态 |

阶段出口：由提议者确认「整体方向是否对」「哪些参考细节必须保留」，再确定正式开发范围。

### 第二阶段：接入真实状态

- 先定义状态来源与优先级，区分真实任务状态、用户手动操作、纯装饰动画。
- 如果展示忙碌、休息等状态，明确它是系统事实还是角色演出；不能仅凭随机动作声称机器人正在执行某项任务。
- 保持机器人之间的数据和形象配置隔离；「全部机器人」视图如何展示需另行确定。
- 场景交互不得绕过现有钱包审批与权限。看到一个物品或播放一次动作，不应自动扣款或生成购买记录。
- 前端待机动画不应持续触发模型调用；确需模型决策时，单独设计触发条件、预算和关闭方式。

### 暂不纳入最小版本

家具自由摆放、购买后自动布置、群友访问和送礼、多机器人同居、复杂寻路、真实支付、桌面宠物、VRChat 联动。这些可能是后续方向，但本次找到的群聊不足以支持把它们列为已提出需求。

## 开发前待确认

1. **视觉目标**：Live2D 是否必须？优先追求立绘互动、房间生活感，还是状态看板？
2. **视频参考**：已查看消息 `996661569` 的 8 张抽帧，需补看连续视频，确认过渡动画、触发方式及是否真实联动聊天与工具。
3. **资源来源**：使用谁的角色模型与背景？是否允许随 Diana 分发、修改、在 Web 中使用？
4. **动作驱动**：由用户点击、真实任务状态、时间规则还是模型决策驱动？第一版选一种主机制。
5. **功能边界**：仅做可视化，还是本期必须同时接入房间物品与钱包？后者应单独估算。
6. **访问范围**：继续仅在管理界面使用，还是需要向群友开放？开放访问必须另做身份和权限设计。

## 建议验收标准

以下为进入实现阶段后的验收草案，不是群聊中已经约定的指标。

- 打开小窝能够看到选定机器人的形象与房间，原有钱包和动态仍可正常访问。
- 至少展示一组经确认的动态效果；演示状态与真实状态有明确区分。
- 桌面和手机均能查看核心场景与操作，模型不遮挡导航、按钮或正文。
- 模型加载失败时有可理解的提示和静态回退，不出现整个页面不可用。
- 切换机器人不会串用状态或配置；关闭可视化后仍可使用原有功能。
- 页面隐藏或离开后停止不必要的渲染；提供减少动画的方式，不因待机持续消耗模型额度。
- 开发后在 demo 模式做浏览器目视验证；涉及状态、配置键或权限时补充相应测试。

## 推荐下一步

先围绕抽帧中已观察到的「床上持手机—床与书桌之间—坐在电脑前」三个画面状态确认预期和 Live2D 的必要性，再做单房间、单角色的状态联动原型；完整视频补验与技术选型并行进行。暂不扩展为装修游戏或自主生活系统，避免把群里的视觉诉求膨胀为未经确认的大功能。
