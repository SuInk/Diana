# Pi Telegram Agent 对照优化与回放

## 参考与范围

参考 [mizorewww/pi-extension-telegram-agent](https://github.com/mizorewww/pi-extension-telegram-agent/tree/31e34e70d14507b09f105d2165d1377d65247b50)
的 `docs/cache.md`、`src/agent/extensions/codemode.ts` 和 `src/agent/prompt.ts`。

可直接借鉴的是：只追加已发送前缀、限制每轮新增上下文、把独立工具调用合并处理。
参考项目的 Code Mode 使用 Node 托管 QuickJS WASM。第一阶段优化 Diana 原有的
`tool_search` / `tools_execute` 路径；后续新增同源 `pi-codemode` 的能力受限脚本入口，
继续经过 Runner 门禁，不把宿主机命令执行或 Node 本身当作模型脚本的安全边界。

## 生产排查

从 miku 只读提取 2026-11-01 的 1,089 条主回复模型请求，其中
709 条使用 `gpt-6.1-terra`。这不是全部平台的长期统计。

- 709 条中有 384 条包含连续两版相同的发言者工具环境，最后一版平均约 4,041 字符。
  这些请求可能处于同一轮工具循环，不能把请求数当作独立会话数。
- 一条生产响应同时请求了三次 `tools_execute → browser_render`。
  后续工具消息证明只执行了第一条，另外两条返回未执行提示。
  原因是并行白名单检查外层名称，只接受 `browser_render`，不接受封装调用。

原始消息、请求、密钥和完整模型回复不提交到仓库。

## 改动与边界

1. 给 Runner 生成的发言者工具环境添加专用标记。续接时，只在最新一版完全相同的情况下
   省去新副本；不删除、改写历史前缀。不跳过时钟、当前用户消息或其他状态提示。
   A → B → A 必须重新追加 A，用户/工具输出不能伪造 system 块来触发去重。
2. 并行判断解析 `tools_execute` 的内部只读目标，继续使用原契约校验、禁用操作检查、
   hooks、工具预算、超时、输出遮罩和截断。执行记录用真实工具名，供应商历史保留原信封和调用 ID。
3. 只有 `web_search`、`browser_render` 可并行。写入、配置、发消息等不扩大并行权限。
   工具结果按请求顺序返回，不按完成顺序；搜索结果仍走紧凑呈现。
4. 真实三页回放发现正文选择错误：浏览器成功打开页面，但三个结果的正文都是同一条
   无关推荐卡片，导致重读和额外模型调用。提取器原先无条件优先选第一个 `article`。
   现在当它不属于 `main`，或没有包含 `main` 的主标题时，保留主内容区；主标题位于
   `article` 内的 README 类页面仍优先提取文章，避免文件列表挤占正文。

少追加工具环境可以减缓上下文增长、减少新输入 token，并推迟长度上限触发的重建。
它不保证网关缓存命中，也不能将模型 API 耗时等同于 QQ/Telegram 投递耗时。

## 验证方法

单元测试覆盖直调/封装并发、调用 ID 和信封保留、非法参数、禁用操作、工具缺失、
写入工具不并行，以及环境相同/变化/恢复、用户伪造标记和时钟不去重。

真实模型回放入口：`TestLivePiEnvironmentReplay`。从生产取一条包含完整工具环境的请求，
两组使用相同首轮输入及当前生产模型 `gpt-6.1-terra`；后续两轮追加相同的无副作用追问。
旧组每轮重复环境，新组调用实际去重函数。分别记录 input、cached input、output 和 API 墙钟耗时。
模型生成的工具调用仅记录，不执行、不向真实群发消息。

私有样本 JSON 包含 `request`（`llm.GenerateRequest`）与 `environment`（对应 system 正文）。
提供 `DIANA_LIVE_LLM=1`、`DIANA_TEST_LLM_CONFIG_JSON`、`DIANA_PI_REPLAY_SAMPLE` 和
`DIANA_PI_REPLAY_RESULTS`，通过 `scripts/test-serial.sh` 执行；不得将密钥写入仓库。

这是生产首轮加受控追问的小样本对照，不是线上灰度，也不是六条独立生产会话。
首轮可能因供应商缓存驻留、账户路由而冷热不同；续接轮应单独汇总，命中率按 token 加权计算。

## 工具编排端到端对照入口

`TestLivePiParallelReplay` 固定生产中三次 `tools_execute → browser_render` 的首步请求，
实际访问这三个公开网页，再让当前模型根据真实工具结果继续。首步是录制调用，不计入真实模型
请求数；后续调用全部走实际配置的模型。旧版和新版使用同一测试文件，不对旧版添加人工延迟。

测试使用独立工作目录、无登录态沙箱浏览器，不连接群消息发送通道；工具调用只允许这三个 URL。
收尾前必须完成三页读取，避免旧版漏读而看起来更快。`DIANA_PI_PARALLEL_REPLAY=1`
显式启用，`DIANA_PI_PARALLEL_RESULTS` 指定私有结果文件。和其他测试一样通过
`scripts/test-serial.sh` 排队执行。

首次新版和旧版运行分别在 70.67 秒、73.41 秒因未满足三页读取完整性而失败。
这两次耗时不是成功完成相同任务的对照，**不计入提速结果**。
回放工具现在保留失败步骤的私有诊断记录，供区分真实网页/浏览器失败与验收判定问题；
不能仅凭模型最终回复或较短耗时宣布读取完成。

后续诊断证实并非浏览器打开失败：三次调用均成功，但 `text` 都只有同一条约 65 字符的
推荐内容，而 `title`、`requested_url` 正确。修复上述正文选择后，两组对照都使用相同的
正文提取修复，只保留工具分发实现的差异。这样测的是并行分发收益，不能把正文修复的收益
混入分发对照；最初两组未完成任务的耗时仍不参与比较。

修复正文后，带 `-race` 的真实浏览器和 `gpt-6.1-terra` 回放两组均通过：

| 成功读取页面数 | 3 | 3 |
| 真实模型 API 请求数（不含固定首步） | 3 | 1 |
| Runner 完成耗时 | 43,990 ms | 18,768 ms |

| 输出 token | 444 | 310 |

本例完成耗时减少 57.34%，输入减少 51.81%。三页单独读取都约 11～13 秒；
原分发被迫逐步补读，新分发一次并行读取，再用一次模型请求收尾。
两组结果均给出三页标题及概括，并明确第一页没有更多正文，没有把推荐卡片当成文章。
缓存 usage 未提供正值，本组不作缓存命中率结论。

这是单组三页任务，执行顺序为新版后旧版，没有对所有群聊延迟作统计推断；
首步调用固定、任务提示受控、后续模型请求与网页读取真实。它测到的是回复生成阶段，
没有测量 QQ/Telegram 发送 API 的网络投递耗时。
