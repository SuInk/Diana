# 输出格式、主回复缓存与 Code Mode 生产回放

数据来自 miku 生产库和 debug-traces（2026-10-31～11-02，只读）。原始消息、请求和模型回复不提交到仓库。
回放经 Diana 自己的 `llm` 客户端、生产同一 sub2api Responses 端点和配置档发出。devin/swe-2 上游
回放期间持续 429/503，重试后仍失败，所以在线回放统一用同为生产主力的 `gpt-6.1-terra`。

## 1. Code Mode：子调用拿到被截断的字符串

### 线上故障

11-02 一条「算下你的用量」主回复跑了 9 轮、输入 66 万 token。脚本 `tools.llm_usage({scope:"all"})`
的原始结果约 16.3 万字，Runner 按模型侧上限截到 2 万字并追加一句中文说明再交给脚本，JSON 从中间断开，
`json.Unmarshal` 失败后脚本收到的是字符串：`r.groups` 为空、汇总全是 0，`Object.keys(r)` 列出逐字下标，
两次撑爆 32KiB 输出上限。

### 改动

- 子调用改交未截断的已脱敏原文，上限 512KiB（低于 1MiB 帧上限）；超限时抛出可 `catch` 的错误，提示缩小范围。
  审计记录仍按原上限截断。
- 返回值去掉对象里的 `null` 成员（保持原键序），编码时不再把 `< > &` 转成 6 字符的 `\u` 转义。
- 工具说明补充：单次调用直接调原工具、子调用返回完整原始结果、结构不明先 `return Object.keys(r)`。

### 验证

| 生产脚本 | 旧输入（截断字符串） | 新输入（完整对象） |
| --- | --- | --- |
| 1 汇总各群用量 | `output_limit` | 正确汇总 8 个群 |
| 2 读 `r.usage` | `{}` | `{}`（字段本就不存在，模型猜错） |
| 3 返回 JSON 字符串 | 全 0、`groups:0` | 正确汇总 |
| 4 `Object.keys(r)` | `output_limit` | `["group_id","groups"]` |

输入用生产 trace 里真实的 `llm_usage` 结构复制到约 12 万字，直接驱动嵌入的 host。

说明改动的行为回放：生产两天 809 次带 codemode 的主回复请求里只有 7 次选了它。取这 7 次加 8 次选了
单次 `browser_render`/`web_search`/`llm_usage` 的请求，新旧说明各跑（codemode 组 2 样本、对照组 1 样本），
0 错误。对照组两臂都是 0 次 codemode，没有诱发滥用；原先「单次 web_search 包一层原样返回」那条两臂都
直接调用工具。两臂输入 token 基本相同。

## 2. 主回复缓存：成员都能用的工具规则留在了尾部

### 诊断

按同群相邻两次首步请求算最长公共前缀，和实际命中对比：terra 离线 56.0%、实际 56.1%，损失基本都来自
提示词结构；swe-2 结构上限 60.3%、实际 28.3%，另有供应商侧损失。

分叉位置排查的结论（损失占全部输入字符）：

- 「更早的图片与文件索引」和窗口滑动几乎同时变化，单独挪走只多 0.5～0.7 个百分点，未改。
- 跨群历史在生产里已经排在本群历史之后，挪动反而更差，未改。
- 尾部每次重算的大块：发言者按需工具目录（约 8K 字）、对话对象段（约 3.9K 字，其中约 1.7K 是固定的工具规则）。

github、subscription、cross_session_message 因工具定义随发言者变被归入 `speakerVariantTools`，它们的
规则文本也跟着进了尾部；但规则本身对谁都一样，只取决于本群成员能不能用这个工具。代码里 cross_session
那段注释本来就写着「对所有人逐字相同，所以进稳定头部」。

### 改动

规则位置改按「本群非主人成员能否使用该工具」判断；工具定义仍留在尾部按需目录。仓库订阅规则只对管理
人员出现，固定留在尾部。

### 验证

- 离线（10-31～11-02 全部同群相邻首步请求）：swe-2 388 对 66.4%→67.5%，terra 208 对 68.2%→68.9%。
  第一版把仓库订阅规则也挪进头部，模拟结果反而降到 61.0%，据此改回尾部。
- 在线（两个群各 5 条连续首步请求，各臂加随机前缀冷启动）：续接 8 次命中 46.3%→47.7%，每次复用的头部
  从 18,048 增到 19,072 token。
- `TestReplyPrefixSameForOwnerAndMember` 增加断言：私聊转发规则在主人与成员共享的头部，仓库订阅规则不在。

工具循环内部的续接轮（terra 76.7%、swe-2 71.6%）实测每轮只比上一轮请求少复用约几百 token，
尾部临时消息重挂造成的损失很小，未改。

## 3. 输出格式

生产近 3～7 天机器人出站消息：OneBot 4308 条里 HTML 标签 1 条、`**` 漏出 1 条；QQ 官方与 Telegram 的
Markdown 由适配器渲染。

### 改动：HTML 行内标签

模型偶尔用 HTML 代替 Markdown（生产 OneBot 出站「…来做<br>扩展你随便加…」，terra 回放在 QQ 官方上写
「要花多少<s>钱</s>」），三个平台都不渲染 HTML。`normalizeReply` 里统一处理没有属性、同一行成对的
`<br> <b> <strong> <i> <em> <s> <del> <strike> <u> <code>`：富文本平台换成对应 Markdown，交给适配器按能力
渲染或降级；纯文本平台只留文字。代码块和行内代码里的标签不动，Diana 自己的 `<diana-…/>` 标记不受影响。

### 回放

- 富文本（Telegram 7 条、QQ 官方 3 条，现行规则）：列表、加粗、代码块和 `[标题](网址)` 使用得当，
  闲聊未硬加格式；偶见 QQ 官方上的行内代码（适配器已降级）和上面的 `<s>`。规则不改。
- 纯文本（OneBot 12 条，生产现行规则 vs 已合并的 PR 1388「纯文本平台列表改用数字编号」规则，各 2 样本，
  0 错误）：模型原文里新规则去掉了加粗和 Markdown 列表，空行变多；把输出送进真实的 `normalizeReply` +
  `splitEventChatReply` 数气泡，默认配置每条 1.61→1.78 个，开换行分条 1.94→2.00 个，两臂都没有超过 5 条，
  送出文本都没有 Markdown 残留。空行段落会被整段保留成一条再收拢，对用户可见的影响很小，纯文本规则不再改。

## 另见

成对的机器人消息。属于投递层问题，不在本 PR 范围。
