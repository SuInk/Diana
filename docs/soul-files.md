# 人设文件 soul.md

人设正文可以摆成文件来写，每台机器人一份：`<souls_dir>/<机器人 ID>.md`。默认不启用，在 `config.yaml` 里设 `storage.souls_dir` 后生效（例如 `souls_dir: souls`，路径相对进程工作目录，和 `db_path` 一样）。

## 它是导入/导出源，不是运行时真相源

人设正文是系统提示词稳定头部的第一行，运行时每条消息都要读，还要支持分群覆盖和 WebUI 随时改。所以文件不能当运行时的真相源，否则同一段人设会有两个互相覆盖的来源——`bot` / `llm` 配置一贯的规矩就是「数据库是唯一真相源，YAML 只在库空时播种」（见 `config.example.yaml` 开头）。

文件的定位因此是：给人写。几千字的人设塞在 WebUI 文本框里难写、难 diff、难进版本库，摆成 `.md` 就都解决了。权威副本始终在数据库，WebUI、分群覆盖、人设迁移逻辑一行都不用改。

## 同步规则

启动时同步一次（赶在机器人 Start 之前，文件里改过的人设从第一条消息起就生效），之后每 30 秒对一次。轮询而不是监听文件事件：目录可能在网络盘、容器挂载卷或 Windows 上，事件可靠性各不相同，而漏掉一次事件比晚半分钟生效糟得多。每轮只读几个小文件、比几个哈希，两边都没变就一个字节都不写。

文件头部的 `synced_hash` 记着上次同步时正文的哈希。人改文件不会顺手改它，所以它和文件正文、数据库人设各比一次，就知道这一轮是谁改的：

| 情况 | 结果 |
| --- | --- |
| 文件不存在 | 按数据库里的人设新建（`created`） |
| 两边正文一致 | 什么都不做（`unchanged`） |
| 文件存在但没有 `synced_hash` | 首次接管，以文件为准导入数据库（`imported`） |
| 只有文件变了 | 导入数据库（`imported`） |
| 只有数据库变了 | 写回文件（`exported`） |
| 两边都变了 | 保留数据库那份并重写文件，文件那份另存为 `<机器人 ID>.conflict-<时间>.md`，打一条日志（`conflict`） |
| 文件正文为空 | 不导入，按数据库那份重写文件（`exported`），不留冲突副本 |

两边都改时不猜哪边更新：直接覆盖会悄悄吃掉一份手写的人设。空正文不当成「把人设清空」——更可能是编辑器写坏了或文件被截断。

## 文件长什么样

```markdown
---
bot: 主号
profile_id: bot-a
synced_at: 2026-09-21T14:03:11+08:00
synced_hash: sha256:…
---

<!-- 这一段之下是人设正文，改完保存即可：下次同步会导入数据库。
     synced_hash 由同步维护，不要手改；它用来分辨这次是你改了文件还是在 WebUI 里改了人设。 -->

身份与来历：你叫……
```

- 文件名用机器人 ID 而不是名字：ID 不会因为改名而变，改个显示名不该让同步认不出这是同一台机器人。`bot:` 那行只是让一目录的 `<ID>.md` 认得出谁是谁，不参与同步判断。
- 手写一份纯 Markdown 扔进去就能用，不必先补 front matter：没有 `synced_hash` 时按「首次接管」以文件为准导入，导入后同步会把 front matter 补上。
- 我们写进文件的 HTML 注释是给人看的说明，导入时会被剔掉，不会当成人设正文发给模型。
- 写文件是原子的（同目录临时文件 + 改名）：同步中崩溃不会留下半截人设，而那正是下一次启动要拿来导入数据库的内容。

## 边界

- 分群覆盖的人设不在文件里。文件对应的是机器人级人设正文（`system_prompt`）；某个群单独覆盖的人设仍然只在 WebUI 和数据库里。
- 自述（自我认知）不在文件里，它是模型自己写的，见 [self-notes.md](self-notes.md)。人设文件只有人能改。
- 没接入机器人配置存储的部署无法导入，同步会报错并跳过那一台，不影响其他机器人和启动。
