# 工具描述写法

工具定义每轮都随请求发出：每轮带完整定义的放在 `tools` 字段，按需加载的在加载后把整份契约留在系统提示词末尾，目录里还有一行摘要。重度群一次主回复里工具相关内容一度占到输入的四成，其中大半是描述文字，参数说明（约 1 万 token）比主描述（约 8 千）还多。

写法参照 Codex CLI 和 opencode：工具描述说清「做什么、什么时候别用」，参数说明只说「是什么、什么格式」，用法细节交给出错时的返回信息。

## 主描述（`Description()`）

- **第一句就是摘要**，说这个工具做什么，最好不超过 40 字。按需工具的目录只截前 120 字（`SystemPromptToolDescriptionBudget`），模型靠这一句决定加不加载。
- 第一句写成动宾句（「找仓库、搜索和管理 GitHub Issues……」），不要压成「GitHub 仓库、Issue 和 PR：……」这种名词清单。回放里 github 的第一句这样一压，主人让改好感度时 gpt-6-sol 有 6/10 次先拿 github 随便搜一个词，换回动宾句后 0/8。
- 后面只写模型不说就会做错的约束，每条一个短句：
  - 和相近工具的分工（「一次性提醒用 reminder」），只写一次，不在参数里重复。
  - 权限（「仅主人」）、不可撤销的副作用、必须先做的前置步骤。
  - 线上出过事故的规则保留，压成一句，不讲来龙去脉——来龙去脉写在代码注释里。
- 不写：参数逐个复述、用户原话举例（最多留一个能决定路由的）、「必须」「务必」「禁止」之类加重语气、为什么这样设计。
- 目标 150 字以内，上限 300 字。

## 参数说明（schema 里的 `description`）

- 一个短句：含义 + 格式 + 默认值或范围，目标 30 字以内，上限 60 字。例：「首次触发时间，RFC3339」「留空为默认分支」。
- 名字和枚举已经说清的参数不写说明，或只写一个名词（「订阅 ID」）。只解释不显然的枚举值。
- 多操作工具的 operation 说明里，不显然的操作要说出它做什么。relationship 的「set/adjust 仅主人」只说了权限没说是改好感度，回放里模型就不确定该用它。
- 互斥写成「与 X 二选一」；仅对某个 operation / kind 生效写成「create 专用」「kind=rss」。
- 不写使用场景（「用户说……时传」）、不举多个例子、不重复主描述里的分工说明。
- 嵌套 `items` 里的同名字段只写最短的一句，不把外层说明再抄一遍。

## 用法细节放哪

- 填错的情况由代码校验并返回具体原因（「interval 最短 5m」「月请写 mo」），模型看到错误再改。比把每种边界提前写进说明省得多，也不会漂移。
- 跨工具的流程放系统提示词的规则段，用 `hasAnyTool` 判断工具在场时才带。
