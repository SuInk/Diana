# 聊天切换模型

主人可以要求切换当前机器人的对话、视觉理解、意图识别或图片生成模型。机器人会通过 `llm_config` 工具完成修改；普通用户、其他机器人的主人及未开启“允许主人修改模型配置”的机器人不能执行。

工具的 `list` 操作返回已配置供应商的 ID、名称、协议和已缓存模型名称，不返回地址、密钥或请求头。跨供应商切换优先使用 `provider_id`；也支持准确的 `provider_name`，重名时必须指定 ID。旧 `provider` 参数继续表示协议类型，不能拿它代替某家具体网关。

例如，可以说“列出可选的供应商和模型”，再说“把你的对话模型切到 Gateway B 的 shared-model”。供应商必须已在 WebUI 中配置；工具不创建供应商，也不修改其地址、密钥或默认模型。同模型存在于多家供应商时应明确指定；仅给模型名时优先保留当前可用绑定，当前不支持且其他候选不唯一则拒绝猜选。

切换先校验供应商、注册表及后端模型列表，再只保存消息所属机器人的对应用途。缺少机器人范围、机器人不存在、模型不可用或保存失败时不修改运行态，不会回报成功。正式存储路径在保存成功后更新内存，保留当前激活机器人、其他机器人、其他用途以及无关配置。

切换只调整该用途的模型顺序：目标已经在列表中时移到首位，其余模型相对顺序不变；目标尚未列入时添加到首位，旧主模型和后备都保留。跨供应商也不会清空列表。分组绑定及各条路由的权重、停用、standby 和思考强度保留，用途的调度策略不变。后续调用仍遵循原调度策略、健康避障和停用规则，因此排到首位不代表每一次请求都会选中它。

改完会向 WebUI 播一条配置变更通知。开着控制台不用手动刷新：机器人页的「模型分配」直接换成新值，列表页和其他页签同样跟上。正在编辑这台机器人、而且模型分配那几行也改过时不自动替换，页面挂一条提示说明别处已经改过，由主人决定是载入最新还是继续保存自己的草稿。屏蔽名单、禁用群这些聊天指令改的也是同一份机器人配置，同样会播这条通知。

模型列表校验确认目标在供应商公布的可用清单中，不代表已经完成一次真实生成或保证未来额度可用。当前正在生成的这一轮可能继续使用已经创建的模型客户端，新分配在后续调用中生效。

## 模型调度模式

机器人页的「模型」按用途选择调度方式，下拉顺序为「智能切换、主备切换、轮询、加权轮询」。支持智能切换的用途默认使用智能模式，旧配置缺省或空值也按智能执行；显式选择主备时保存 `failover`，轮询和加权轮询保持原策略。独立图片生成、语音与视频等尚未接入健康排序的链路不显示智能选项，缺省仍为主备；跟随用途沿用被跟随用途的调度策略，不单独保存策略；后备条目也不保存策略，只保留权重、停用及 standby 等路由属性。

- **智能切换（smart）**：按配置顺序选择，只把正在冷却的候选挪到后面；冷却一结束，主模型立即回到首位。历史失败次数只决定下次再错时冷却多久，不参与排序，也不会把没在冷却的主模型压到备用后面。保持顺序也让同一渠道的提示词缓存持续命中。停用模型不参与，standby 保留独立后备位置，不会抢在健康常规候选之前。一次运行中的后续请求仍沿用当前渠道。
- **主备切换（failover）**：按配置顺序尝试主模型和后备。
- **轮询**：在常规候选间均匀分配，失败再尝试其他候选。
- **加权轮询**：按配置权重分配，分组中的每个兼容渠道使用该行权重。

后三种模式保留自己的选取规则，与智能模式共用下面的避障机制。智能与主备的区别是排序阶段就把冷却候选挪后（主备保留原列表，由调用层跳过冷却候选），实际尝试顺序相同。智能排序不读取剩余额度、不计算成功率，也不修改保存的列表顺序。

## 聊天启停模型与调度策略

主人或管理员可直接说“停用对话里的 Gateway B / other 模型”“重新启用这个模型”或“把对话调度改成轮询”。Agent 先用 `llm_config list` 查看当前列表，再使用 `enable`、`disable` 或 `set_strategy`。启停通过模型 ID 和提供商 ID（分组路由用分组名）匹配已有路由，同名歧义会拒绝执行；不会添加模型或调整顺序。停用最后一条模型后该用途将不可用，回执会说明，可在 WebUI 恢复。

策略支持 `smart`（智能）、`failover`（主备）、`round_robin`（轮询）、`weighted`（加权）；图片生成不支持智能。切换策略保留每条模型的权重、启用状态和思考强度。跟随其他用途的模型须明确操作被跟随的用途。

这些操作仅支持 `scope=bot`，不支持当前群独立启停或策略；不会把“仅本群”的请求扩大为整个机器人。沿用聊天模型配置开关、管理员权限及安全模式限制，保存成功后才更新运行态。不调用上游测试接口，也不会把配置修改回执写成模型测试通过。

2026-10-31 在 miku 使用当前 `gpt-6.1-terra` 和与运行时一致的非严格工具 schema 做隔离回放：停用指定提供商模型、重新启用及切换轮询策略均生成正确参数。输入为合成配置，未执行模型返回的线上写操作、未发送平台消息；工具执行和持久化由本地回归测试验证。

## 自动避障与恢复

各调度模式共用故障避障，尊重 standby 和停用设置；避障无需独立开关，也不修改保存的模型分配。健康状态按配置档与模型分别记录，不代表实际剩余额度。

- 额度耗尽、鉴权失败及模型不可用直接尝试其他候选；HTTP 429 限流、5xx 和连接故障先在同一候选有限原地重试，再切换。结构化上游状态码优先于错误文本中的数字。
- 健康故障达到次数后触发冷却，具体次数和时间见下表；没到次数时只是这次请求改用备用，下次仍先用它。冷却是暂时跳过该候选，不是让当前请求等待冷却结束；有可用备用时会继续尝试备用。
- 存在未冷却候选时，跳过仍在冷却的候选，不在其他候选失败后重新撞它们。所有候选均冷却时，只有限探测最早恢复的一个；只有一个候选时仍保留调用机会。冷却结束后，该候选重新参与所选策略的调度；智能和主备模式下排在前面的候选会立即回切。
- 调用方取消或整次请求截止后立即停止。内容策略拒绝、上下文溢出和能力不匹配继续使用各自的处理规则，不当作供应商健康故障。

### 重试、冷却与恢复时间

| 故障类别 | 当前请求的处理 | 何时冷却 | 首次冷却 |
| --- | --- | --- | --- |
| HTTP 5xx（含 Cloudflare 520–524/530）、408，以及连接中断、连接被拒等瞬时故障 | 允许重试时，默认在同一候选等待 700 毫秒后重试，最多 2 次；仍失败再切备用 | 连续第 3 次失败 | 10 秒 |
| HTTP 429 限流、并发超限 | 同上，先原地重试再切备用 | 连续第 3 次失败 | 1 分钟 |
| 模型不可用 | 直接尝试备用，不原地重试 | 连续第 3 次失败 | 1 分钟 |
| HTTP 402 及带额度、余额、账号池限住字样的 429/5xx，HTTP 401/403 鉴权失败 | 直接尝试备用，不原地重试 | 第 1 次失败 | 1 分钟 |
| 上游提供有效 `Retry-After` 或可识别的等待提示 | 对需要冷却的故障优先采用上游时间，不额外翻倍 | 第 1 次失败 | 按提示，最多 30 分钟 |
| 单次模型请求超时、空输出 | 按错误类别和剩余预算重试或切换 | 不计健康冷却 | — |

「连续第几次失败才冷却」默认 3 次，可在机器人「模型」页的「自动恢复规则」里改（`failures_before_cooldown`，1–10，1 表示一失败就冷却）；重试次数、重试间隔和各类冷却时长也在那里调整。上次失败或冷却结束后隔了 **10 分钟**才再失败，按新一轮从 1 数起。

网关把额度或账号池限流包装成 429、503 等错误时，优先按额度处理，不原地重试，第一次就冷却。调用方取消或整次请求截止不适用上表中的重试。

没有有效上游等待提示时，进入冷却后每再失败一次时长翻倍，单次冷却上限为 **30 分钟**。从首次冷却算起，同类故障连续发生的时长依次为：

- 瞬时故障：**10 秒 → 20 秒 → 40 秒 → 1 分 20 秒 → 2 分 40 秒 → 5 分 20 秒 → 10 分 40 秒 → 21 分 20 秒 → 30 分钟**，之后保持上限。
- 限流、额度、鉴权及模型不可用：**1 分钟 → 2 分钟 → 4 分钟 → 8 分钟 → 16 分钟 → 30 分钟**，之后保持上限。

失败次数按“配置档 ID + 模型”累计，不按错误类型分别累计；故障类型变化时，用本次故障的基础时长结合累计失败次数计算。计数是候选调用失败后的健康记账，不是把候选内部每次重试分别算一轮冷却。在原冷却期间提前探测又失败时，截止时间只会延长，不会缩短。

冷却到期只恢复候选参与原有路由的资格，**不会启动后台定时探测，也不会立即清空失败次数**。后续请求选中并调用成功后，立即清除该候选的冷却及失败计数。失败记录从最近一次健康故障起保留 **24 小时**，只用于计算再次失败时的冷却时长；这是状态保留时间，不是冷却时长。冷却到期但计数未清零的候选照常按配置顺序参与调度，不会因残留计数排到备用后面。状态保存在进程内，不持久化到配置，重启后重新累计。

所有候选都在冷却时，只提前探测最早恢复的一个；只有一个候选时也仍允许调用。因此这里不是严格熔断，不能理解为“冷却期内绝不会访问上游”。同一候选的“冷却中被跳过”日志最短间隔为 **10 分钟**，仅用于日志节流，不影响请求调度。

### 单次模型请求超时

在机器人「模型」页的聊天模型下设置「单次模型请求超时（秒）」。该值是机器人级设置，API 字段为 `model_request_timeout_ms`（毫秒），与全局提供商的超时设置分开。

- 正数限制每次底层模型生成尝试的最长时间，包含等待响应和整个流式接收过程；持续心跳或持续输出也不会延长这个硬上限。
- 同模型重试、上下文收缩后的重试、切换候选以及工具执行后的下一次模型调用，都重新计时。单次硬上限到达后，不在同一候选额外重试，而是尝试下一候选；不因此增加健康失败次数或冷却。
- `0` 表示不增加单次硬上限，旧配置缺失该字段时同样按 `0` 处理。提供商自身的响应头或空闲超时仍生效，也可能比设置值更早终止请求；若提供商也没有超时设置，请求可能一直等待，因此建议配置正数。
- 普通聊天不再套用原先默认 180 秒的整轮总时限，模型切换和工具循环不会因为累计达到该时间而停止。仍保留调用方取消、服务关闭、最大执行步数，以及工具、路由判断和独立后台任务自身的时间预算；不移除这些独立保护。旧 `request_timeout_ms` 字段保留用于兼容仍使用它的独立任务，不再限制普通聊天整轮耗时。
- 单次设置作用于机器人共用 LLM 调用链中的对话和理解用途，不代表独立图片生成、语音、视频或工具执行也受同一限时控制。

例如设置为 60 秒，前两个候选都达到单次上限时，第三个候选仍可获得新的单次预算，不会因为前两次累计耗时而触发普通聊天总截止。不过，这不保证一定调用第三个：前一候选成功、输出已经发送、不可切换的错误、候选停用或冷却等情况仍遵守既有规则。已有可见输出后的超时不会触发换模型重发，详见下面的流式安全边界。

### 流式输出与工具调用边界

流式开流和读流共用单次生成的候选重试预算，候选耗尽后不会从头再跑一遍非流式后备链。只有明确不支持流式的客户端才在当前候选内使用非流式兼容调用。

一旦文本观察器确认可见预览已发送，或无法排除已发送，后续失败不会再原地重试、换模型或改用非流式，外层也不会再调用模型生成第二份收尾回答，避免把两份答案拼在一起。仅在内存中收到文本不算已发送；观察器明确未发送时，局部文本可以丢弃并在预算内重试。工具调用仅在完整成功响应后交付，切换会保留本轮已完成的工具结果，不会重跑已完成的工具操作。

### 能力边界

智能切换只使用调用中的健康故障记录，不读取或推算实际剩余额度，不按额度窗口、余额比例或成功率排序。有可用候选就跳过冷却候选，全部冷却时仅探测最早恢复的一个；具体重试和恢复时间遵循上表。

## 联网搜索统一全局配置

在「提供商 → 搜索提供商」编辑全局搜索开关、首选与后备来源、结果数、超时和链接策略，点击「保存全局搜索」后对所有机器人生效。切换提供商页签保留未保存草稿；保存失败不清除草稿，也不报告成功。机器人页只显示模型，不再提供搜索分配或校验历史搜索字段。

关闭搜索仍保留已选来源；重新启用必须有首选来源。全局关闭或显式空路由（`provider_ids=[]`）不产生搜索工具，浏览器自动补搜也不能绕过。首次未配置路由时仍沿用历史全局 `search_mode`，默认使用浏览器搜索引擎；缺失路由与显式空数组不同。

历史机器人 `web_search`、插件 profile 开关／settings 及凭据保留，但不再参与搜索运行时；不会挑选某台机器人的旧密钥或把其整份设置复制成全局值。旧机器人引用不再阻挡提供商删除，当前全局路由的引用完整性仍受保护。机器人配置往返保留历史字段，不会因这些失效字段阻挡无关修改。

## 按群设置聊天模型

在管理界面的群配置弹窗中，通过「本群聊天模型」选择提供商和模型。默认「跟随机器人」；独立选择后，仅该机器人在该群的聊天回复使用选定模型，显式跟随聊天的用途也随之切换。独立配置的其他用途保持原设置，其他群和私聊不受影响。群级选择只记录本群优先模型，运行时将它移到机器人当前列表首位，保留其余模型和后备顺序；未列入的目标临时添加到首位，不改机器人保存的列表。机器人后续增删后备也会反映到本群；切回「跟随机器人」后恢复机器人当前的顺序。

配置保存后在后续调用中生效，正在生成的请求可能继续使用原模型。API 的 `chat_model` 包含 `profile_id` 和 `model`；两者都为空表示恢复跟随，省略该字段保留已有配置，以兼容旧客户端。群级配置按机器人 ID 与群 ID 隔离。主人也可以在群里说“只把本群聊天模型切到某提供商的某模型”，通过 `llm_config` 的 `scope=group` 切换；“恢复本群跟随机器人”对应 `operation=reset, scope=group`。群级切换仅支持 `chat`，仍需主人权限且开启“允许主人修改模型配置”，切换前测试目标模型，失败不改配置。`scope=bot`（省略时的兼容默认值）修改机器人级配置。

## 思考强度与模型能力

思考强度按每条模型路由保存，在模型编辑弹窗中设置。排序、切换或删除首条路由后，实际调用使用所选路由自己的强度；未设置的路由使用上游默认，不继承首条路由的值。已有用途级配置中的强度保留在首条路由上，后备路由需按需单独设置。OpenAI 兼容协议在选定实际模型后，按随包携带的 models.dev `reasoning_options` 校验本次请求，包括备用模型、普通调用与流式调用。不支持的档位先向上取最近支持值，超过最高档再降到最高支持值。例如 GPT-6.1 Sol 的 `none` / `minimal` 会按 `low` 发送，支持 `none` 的模型仍可关闭思考。空值保持跟随上游默认；缺少能力数据时不猜测。DeepSeek 等已有独立思考开关的协议继续使用原来的适配逻辑。

模型编辑弹窗的思考强度下拉框将已知不支持的档位置灰，旧值仍可回显。分组路由对应多个提供商时，只禁用所有候选都不支持的档位；存在能力未知的候选时保留选项，由请求层按实际模型适配。适配会记录模型、请求档位和实际档位，不修改用户配置。

`make build-go`、macOS 打包脚本、CI 完整包和 Docker 构建会运行 `scripts/sync-models-dev.sh`，下载目录并原子替换快照；同步失败时提示并沿用仓库快照。运行时不访问 models.dev。已知提供商优先用其目录数据，私有网关优先使用目录声明的原厂模型定义，其余同名模型仅在档位数据一致时匹配。
