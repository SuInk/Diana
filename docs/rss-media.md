# RSS/Twitter 订阅与媒体

WebUI 通过「筛选方式」下拉框选择「全部推送」「正则匹配」或「LLM 判断」，默认全部推送；正则匹配和 LLM 判断显示并要求填写规则。API/工具的 `judge_prompt` 在全部推送时可留空。全部推送不调用模型筛选，按时间顺序直接推送本次 Feed 中的新条目原文、链接及媒体，不受「单次判断条目上限」限制；选择 LLM 判断时由模型筛选，再按回复要求发送，选择正则匹配时按表达式筛选。已有订阅可选择全部推送并清空规则，未修改的已有规则继续生效。首次创建仍以当前 Feed 建立基线，不补发历史条目；上游已从 Feed 移除的条目不会回溯补抓。原文中的 CQ 控制标记会转为普通文字，不能触发群通知或额外媒体发送。

原文和自然语言回复逐条应用媒体限额，同一来源的所有条目共用 30 秒视频检查预算；按规则生成回复时，每个来源通知应用媒体限额。

RSS 订阅解析 FxTwitter 时间线时，会保留推文和一层引用推文的照片、MP4 视频及封面。共享 Feed 缓存保存这些媒体字段，但它们不会进入 LLM 判断提示词或判断缓存键。普通 RSS/Atom 附件不在此功能范围内。

原文和自然语言回复逐条附带所选条目的媒体，每条最多两张照片和一个视频。按规则生成回复时，只附带回复中明确引用的条目媒体（单条更新无需额外引用），每个来源通知最多四张照片和两个视频，并去重。

RSS 插件设置中的「视频大小上限」（`video_max_mb`）默认 200 MiB，可设置为 1–2000 MiB，独立于链接解析插件的配置。视频必须来自 HTTPS `video.twimg.com` 的 MP4 地址；封面和照片仍限于 HTTPS `pbs.twimg.com`。

发送前通过有界读取核验视频实际大小，最多读取上限加一个字节；即使服务器未提供或错误声明 Content-Length，也不会因此绕过大小检查。每个来源通知的全部视频检查共用 30 秒预算。视频超限、读取失败或超时时，该条目只附封面；封面无效或缺失时保留文字和原推文链接。超出每次通知媒体数量上限的内容仍可通过原链接查看。

视频使用独立消息发送，避免 OneBot 接入端拒绝与文字或图片混发；正文和配图先发送。

通知保存远程媒体地址，重试沿用已作出的“视频或封面”选择，不依赖临时文件。检查成功并不保证平台随后下载成功：如果平台发送视频失败，仍使用现有待发送通知重试机制，不静默声称已送达。

## 验证

离线回归覆盖缓存往返、判断数据隔离、视频大小边界、未知及错误长度、错误响应、取消、跳转限制及 OneBot/Telegram 出站媒体转换。

真实 FxTwitter 在线测试默认跳过，手动运行：

```sh
DIANA_LIVE_RSS=1 go test -race -v ./model/assistant -run '^TestLiveRSSWatchTwitterVideoDelivery$' -count=1 -timeout=3m
```

该测试抓取真实时间线、命中共享缓存，并分别验证正常上限和 1 MiB 上限下的视频与封面结果。它不会自动发送聊天消息。可选 `DIANA_LIVE_RSS_OUTPUT` 指定本地 JSON 输出路径，导出待测试消息供人工联调。

## 正则与 LLM 规则

`rule_mode` 支持 `all`、`regex`、`llm`。省略时兼容旧订阅：空规则为全部推送，非空规则为 LLM 判断。正则和 LLM 共用 `judge_prompt` 保存规则，正则模式要求合法的 Go 正则表达式（最多 2000 字），保存时验证；不支持前后查找和反向引用。例如 `(?i)release|更新` 匹配忽略大小写的 release 或中文“更新”。

正则对每条新内容的标题和正文匹配，任一位置命中即发送所选内容、链接和媒体；正则筛选不调用模型，也不受模型判断条数上限限制。未命中也推进游标；无效的已存规则报错且不推进游标。LLM 模式先判断是否命中，再按独立的回复要求发送。更新时省略规则和类型会保留设置；切换 all 会清空规则。

## 多模态判断（仅 LLM 模式）

判断范围 `media_mode` 默认为 `text`（仅文字），还可选择 `images`（文字和图片）、`video`（加视频画面）、`video_audio`（再加视频音频）。旧订阅仍仅判断文字；全部推送和正则不调用媒体分析。

图片和视频抽样画面先由视觉模型描述并读取可见文字，描述作为不可信条目内容交给 LLM 按规则判断。视频最多抽取 8 帧，按时间顺序分析，不能保证捕获所有瞬间事件。音频模式提取单声道 16 kHz WAV，再调用配置的语音识别模型；没有音轨的视频正常按画面判断。图片无需 ffmpeg；视频需要 ffmpeg 和 ffprobe，语音模式还需语音识别模型配置。

每条最多分析 4 张图片和 2 个视频，图片最多 20 MiB，视频最多 256 MiB 且不超过 5 分钟。超限视为分析失败，不静默截掉剩余媒体。分析上限独立于「视频大小上限」发送设置：分析成功的视频仍可能因发送上限而只发封面。媒体仅接受既有 Twitter CDN 域名，跳转也验证；普通 RSS 附件尚未扩展支持。

`media_failure` 默认 `retry`：记录失败、保留当前来源游标，下次重试；失败不会被当成不符合规则。选择 `text` 则记录错误并退回原始文字判断，丢弃本轮部分分析结果。判断范围和失败选项随订阅持久化，修改不重置已有来源游标。

同媒体、范围和模型授权配置的成功分析在内存缓存 24 小时（有总容量限制），多个订阅复用；模型配置变化、鉴权不可证明一致或带 cookie 的客户端不会跨配置复用。失败不缓存。临时视频、画面、音频处理后删除；共享处理受请求时限约束。媒体摘要进入判断输入和判断缓存键，原始媒体 URL 仍不直接进入判断 JSON。

## 回复要求与模型

筛选方式与回复要求分别设置。WebUI 的“回复要求”直接填写自然语言，例如“直接发原文”“翻译成日语”“用中文总结三点”，不再选择固定的发送模式。留空直接发送原文，不调用回复模型；填写后逐条按要求处理标题和正文，语言和格式由要求决定。图片和视频本身不改写，程序保留原文链接与媒体。全部推送、正则匹配和 LLM 判断都可搭配回复要求。

API/工具使用 `reply_prompt`，最多 2000 字。显式空字符串表示原文；更新时省略则保留原要求。为了兼容，旧订阅未设置此字段时仍沿用 `reply_mode`：original 原文、translated 简体中文翻译、generated 按判断规则生成回复；编辑界面将旧模式转换为可见的自然语言要求。清空并保存后直接发原文，包括原来使用 LLM 生成回复的订阅。

判断模型与回复模型分别用下拉框选择已配置的模型档，空值跟随当前机器人的对话模型路由，不读取 RSS 专用或后台生成绑定，也不覆盖视觉分析或语音识别配置。判断使用 `judge_model_id`；回复模型沿用 `translation_model_id` 字段，兼容已有客户端。专用图片生成、嵌入、语音、视频分组不参与选择，指定配置失效明确报错。

LLM 筛选后按准确原文链接确定命中项；无法确定条目、回复为空或生成失败时保留当前来源游标重试，不将失败当成不符合规则。下一轮可能重新生成回复。回复完成后才开始媒体下载预算。
