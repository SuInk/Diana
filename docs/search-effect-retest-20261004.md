# 新题目联网效果复测（2026-10-04）

## 测试范围

使用 miku 的真实 Gemini 回复模型 `gemini-3.8-flash-medium`、生产插件设置、`Runtime.generateReply` 和一次性沙盒浏览器。测试迁移分支，不替换运行中的机器人，不发送群消息，不写生产数据库。产品提示词在此次复测中没有改动。

新增五题见 [题目 JSON](evals/search-effect-cases-20261004.json)。第一题使用完整 250 条历史消息，其他题只使用生产人设和当前问题。默认框架八题与新题分开记录。

## 判定方式

搜索是否发生、网页是否真正读取、LLM 自动评分、人工查证分开看。自动评分结果只是参考，不能替代一手材料对事实、来源归属、性能表述和比较前提的核对。本次已观察到自动评分漏掉明确错误。

独立查证包括 [Go 官方发布历史](https://go.dev/doc/devel/release)、[Cloudflare Code Mode 原文](https://blog.cloudflare.com/code-mode/)、[OpenAI 并行 function calling 文档](https://developers.openai.com/api/docs/guides/function-calling#parallel-function-calling)、[OpenCode 工具文档](https://opencode.ai/docs/tools/)、[Pi 官方仓库 README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)。独立查证不回填给机器人的调研过程，也不能冒充机器人已读来源。

## 保留的失败与异常

- 长历史下的 Code Mode 适配问题连续两轮只读取第三方 Gist。第一轮给出“快好几倍”等缺乏实测支持的性能表述；第二轮依然没有追到 Gist 正文开头列出的 Cloudflare 原文。不能把原理分析当成用户项目的性能实测。
- 较早一次长历史回放在反驳“只能 Python 串行”时，又说传统 function calling 必须串行。这与官方并行 function calling 文档相矛盾；自动评分仍给了正确且有来源支持，属于漏检。
- 多项目第一轮使用多个 queries 搜索，但 Pi 只读取 Mintlify 文档，没有确认它与官方仓库的归属关系；Memoh 并行编排没有查到，答复如实注明未确认。不能声称已经完成三个项目的官方源码查证。
- 外部题目最初解析到旧题目切片，省略字段继承了旧 Full/Opus 标记，导致部分题目带完整历史和无关的 Opus 评分参考。已改为解析到新切片并完整重跑。前述工具调用和错误回答仍是真实观测，但首次自动评分与预定场景配置不作最终通过依据。
- 修正题目配置后的并行运行中，三个场景因模型网关 HTTP 请求 EOF 中止。搜索已返回结果，不能将其归为搜索提供商失败，也不能当作答案通过；之后改为顺序复跑。单轮恢复不证明网关稳定性问题已经解决。

## 实测触发的通用修复

第一轮多项目调研六个搜索批次都达到输出截断，有些四查询批次最终只留下一个候选。根因是聚合按查询先后拼接结果，格式化先删末尾候选，再删提供商诊断与重复 sources。于是后面的查询虽然成功，相关候选却被截掉。

修复只改变输出预算分配：按查询轮流排列候选，超限时先精简提供商诊断和重复链接列表，再缩减候选；保留每个查询状态、总预算和截断标记。新增四查询大结果回归，验证每个查询仍有候选。不是按 Memoh、OpenCode、Pi 或其他题目硬编码来源。

Go 全量测试和相关 race 测试通过；没有前端或依赖变更。生产服务未部署此次改动。

## 修复后顺序复跑结果

该轮五题的测试流程与 LLM 自动评分全部通过，人工核对结论为三项合格、一项有明确资料缺口、一项不合格。以下耗时仅为 `Runtime.generateReply` 生成完整答复的耗时，不包括之后的独立评分。

| 场景 | 历史消息 | 搜索调用 | 阅读调用 | 回答耗时 | 人工结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| 随口问 Code Mode 是否适合机器人 | 250 | 2 | 1 | 63 秒 | 不合格：只读第三方模式介绍，未追官方原文；性能判断超出已读证据 |
| Go 当前稳定版本、发布日期、安装页 | 2 | 2 | 2 | 61 秒 | 合格：版本和日期与独立官方记录一致 |
| “只能 Python 串行”错误前提 | 2 | 2 | 2 | 68 秒 | 合格：读 OpenClaw 与 Stacklok 文档，列举 JS、Starlark、parallel() 实现；本轮没有再断言普通 function calling 必须串行 |
| Memoh／OpenCode／Pi 联网与调研对比 | 2 | 6 | 6 | 261 秒 | 有资料缺口：读到三个项目官方资料，Pi 回到官方仓库，并如实说明未确认的 Memoh 原生搜索及子代理实现；未完成相关原生源码核对 |
| 明确不联网，只总结给定材料 | 2 | 0 | 0 | 5 秒 | 合格：没有调用网络，也没有增加材料以外的功能 |

多项目六个批次都使用四查询并行。修复前同题有些批次只剩一条候选；修复后六批分别保留 17、14、17、15、15、15 条，五批覆盖全部四查询，另一批覆盖三个成功查询，第四个查询明确返回 budget_exhausted。这证明候选保留问题得到修正，不代表模型选择、查证完备性或性能结论已经稳定。

本轮 Pi 的已读官方扩展文档明确出现 `Tool calls from one assistant message can run in parallel` 与 `pi.registerMcpServer()`，避免沿用旧镜像中“没有任何并行机制／没有 MCP”的笼统结论。Memoh 的已读页面没有进入 web.go／subagent.go，回答保留未确认边界，不能据此断言原生能力不存在。

自动评分将首题也判为正确且有来源支持，人工没有采纳。因此效果判断是：版本事实与明确前提问题已有可用表现，开放式选型和多项目深度调研仍需改进。此次没有为提高通过率改产品提示词、强制搜索／读官网、加入题目匹配代码或恢复终稿复核。
