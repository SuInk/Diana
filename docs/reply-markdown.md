# 简短回复与 Markdown 排版

简短约束限制回答范围，不禁止列表或强调。群聊工具结果收尾和通用收尾提醒都遵循这一边界：只回答问到的内容，多个并列要点可以列出，短答不凑列表，也不为了排版增加事实或重复总结。用户明确指定的格式须逐项满足。

## 原因与边界

原工具收尾提示包含「对方没要详细就不分条列点」，通用收尾又要求「先用一小段」。这些提示会与 Telegram 的富文本说明冲突，使本来适合列表的功能介绍挤成一段。实际生产记录也存在正常列表，因此这不是平台禁用 Markdown，而是生成倾向不稳定。

提示词调整不修改消息分条、长度限制、工具执行或平台的纯文本降级。已有自定义提示词覆盖仍按原有覆盖机制生效，不强制改写用户配置。

- 合成功能材料：原提示的两次回答为 83、75 字，均为单段；候选回答为 131、122 字，均用四项列表和加粗，没有再次添加先前候选中「不用重启」「一条命令启动」的无依据承诺。

## Telegram 引用与剧透

普通消息发送层继续使用 UTF-16 entities；引用与剧透不依赖 Rich Messages：

- 连续以 `>` 开头的行转成一个 `blockquote` 实体；分隔的引用块分别呈现。嵌套引用展平，因为 Telegram 不支持嵌套引用实体。
- `||内容||` 转成 `spoiler`，可跨行；未闭合或转义的标记保留原样。
- 代码内的引用和剧透标记保持字面值；明确包在剧透外壳里的代码优先隐藏内容，放弃不兼容的等宽格式。
- 引用、剧透、强调、链接及提及共享区间更新，删除 Markdown 标记后同步调整偏移；不合法的交叉区间不发送。
- 普通消息的表格策略和通用 Markdown 解析器不变。

生产模型隔离回放另验证了两组显式引用/剧透请求：模型均生成 `>` 和 `||...||`；一组通过 `send` 工具参数返回正文，该工具未执行。格式区间、emoji、提及、代码保护、草稿长度截断以及群聊/私聊分条后的 HTTP 参数由本地测试验证。仍未向真实 Telegram 客户端投递，不能把模拟 API 验证当成客户端目视验收。

## 可选 Rich Messages

在「机器人 → 接入 → Telegram」设置「Rich Messages 富消息」，对应配置键 `telegram_rich_messages`，未配置时默认开启，显式 `false` 保持关闭（包括保存后重启）。保存后按通道配置变更重新建立运行通道。关闭时继续使用原来的 `sendMessage` + entities；旧配置缺少此字段时也默认开启；不兼容的客户端可手动关闭。

开启后，普通 Markdown 用 Goldmark 解析成 typed blocks，通过 `sendRichMessage` 发送，而不是直接把模型原文交给 Telegram 的富 Markdown 解释器。支持标题、段落、加粗、斜体、删除线、链接、代码、引用、有序/无序列表和不超过 20 列的原生表格；金额 `$400-600K` 仍是文字，不自动解释成公式。

兼容边界：

- 提及控制标记、剧透、图片 Markdown、原始 HTML、过宽表格或其他未支持结构，整条消息继续走原有普通富文本路径；不会悄悄丢掉节点。
- 提及和剧透标记只在正文中触发兼容回退；代码中的 `@`、`||` 以及链接目标里的同类字符按字面保留，不会因此禁用原生标题、列表和表格。Diana 控制标记仍整条回退。
- 仍沿用当前分条和普通消息容量检查，不增加单条容量。媒体及其 caption、私聊流式草稿不切换到富消息，最终正文才尝试新接口。
- 只有 API 明确拒绝且表示方法/富消息不支持，才回退一次普通消息。限流、权限错误、无效 blocks、5xx 和网络超时不换接口重发，以免重复投递或掩盖格式错误。
- 服务端接受不代表所有客户端能显示；无法自动检测某位群友客户端的支持情况。遇到“不支持的消息”请手动关闭开关。
- 目前不包含公式、可折叠详情、富媒体块、原生 checklist 或富消息草稿接口。

实现参考 [Telegram InputRichMessage](https://core.telegram.org/bots/api#inputrichmessage) 和 [OpenClaw 的兼容性说明](https://github.com/openclaw/openclaw/blob/9a0ec72eb9ef2678634240b6437c308c033c16b9/docs/channels/telegram/rich-messages.md)。本地测试使用模拟 Bot API 核验 blocks、回复/话题参数以及安全回退条件；UI 在 demo 模式验证开关与保存。
