# Subtask 并行搜索 Worker 设计

## 背景

嘉然当前提供 `subtask` 工具，用于把一段材料和一个明确问题交给独立模型完成。它适合摘要、抽取和局部判断，但还不是一个真正的搜索 Agent：

- 每次调用只处理一个问题；
- 子调用只有模型推理，没有搜索和网页读取工具；
- 子调用不保留任务状态，也不能继续追问或补充检索；
- 主 Agent Runner 每个规划步骤只执行一个工具调用，同一响应中多余的并行调用会被丢弃；
- `scope=vision` 只改变模型配置分组，当前请求并没有携带真实图片输入。

与此同时，资料调研天然适合并行拆分。例如调查一个技术方案时，可以同时查官方文档、现有实现、社区反馈和替代方案，然后由嘉然统一判断。若仍由主 Agent 串行搜索，不仅耗时更长，也会让主对话上下文被大量网页内容占据。

因此，本设计把 `subtask` 扩展为嘉然内部的批量并行、只读搜索 Worker。它不是独立人格，也不直接回复用户；嘉然仍然负责规划、权限控制、结果取舍和最终表达。

## 目标

第一阶段需要实现以下能力：

1. 嘉然可以一次向 `subtask` 提交一个或多个相互独立的搜索任务。
2. 多个任务在后端受控并发执行，不依赖模型在同一个规划步骤生成多个工具调用。
3. 每个任务拥有短 Agent 循环，可以搜索、打开网页、调整关键词并进行交叉验证。
4. 每个任务返回结构化结论、证据链接、未确认事项和资源消耗信息。
5. 单个任务失败、超时或找不到证据时，不影响同批其他任务完成。
6. 兼容现有 `question`、`material`、`scope` 单任务调用。
7. 所有 Worker 默认只读，不能写文件、执行命令、修改配置或发送外部消息。

## 非目标

第一阶段不包含：

- 允许 Worker 再创建下一层 Worker；
- 允许 Worker 直接向用户或群聊发送消息；
- 让多个 Worker 同时修改工作区；
- 把编码代理、图片生成、文档 OCR 等长任务全部合并进 `subtask`；
- 让 `subtask` 自动继承完整聊天历史；
- 建设任意工具、任意权限的完全自治 Agent。

这些能力如果以后需要，应建立在任务权限、持久化、审批和冲突控制已经稳定的基础上。

## 核心决策

### 搜索任务直接交给 `subtask`

对用户而言，嘉然只需要决定“这个问题是否值得拆成若干独立搜索方向”。确定拆分后，由一次 `subtask` 调用提交整个任务组。

```text
用户
  ↓
嘉然：理解问题并拆分搜索方向
  ↓
subtask(tasks[])
  ├─ Search Worker A：官方资料
  ├─ Search Worker B：现有实现
  ├─ Search Worker C：社区反馈
  └─ Search Worker D：替代方案
  ↓
结构化结果集合
  ↓
嘉然：核对冲突、综合判断并回复用户
```

不要求主 Agent 连续调用多次 `subtask`，原因是当前 Runner 会把同一个规划响应中的并行工具调用降级为单个调用。并发必须由 `subtask` 自己的批处理调度器保证。

### Worker 是受限 Agent，不是单次搜索

每个 Search Worker 使用独立的短 Agent 循环：

1. 根据目标生成或修正查询词；
2. 调用搜索工具获取候选来源；
3. 打开高价值页面读取内容；
4. 判断证据是否足够；
5. 必要时更换关键词或补充另一来源；
6. 在预算内生成结构化结果。

这样可以避免把“搜索一次没有结果”误判为“互联网上没有相关资料”，也允许 Worker 对来源进行基本的交叉验证。

### 嘉然保留最终决定权

Worker 输出是调查材料，不是最终回答。嘉然需要负责：

- 判断不同 Worker 的结论是否冲突；
- 区分官方来源、二手报道和社区观点；
- 避免重复计算相同证据；
- 结合用户上下文给出建议；
- 明确说明仍无法确认的部分。

## 工具接口

### 批量调用

建议将新接口设计为：

```json
{
  "tasks": [
    {
      "id": "official",
      "objective": "查找官方文档中与并行 Agent 有关的限制和建议",
      "queries": [
        "official multi-agent orchestration guide"
      ],
      "material": "可选的背景材料",
      "source_policy": "primary"
    },
    {
      "id": "implementations",
      "objective": "调查同类开源项目如何管理并行搜索 Worker"
    },
    {
      "id": "tradeoffs",
      "objective": "查找多 Agent 搜索的成本、延迟和质量权衡"
    }
  ],
  "max_concurrency": 3
}
```

字段约束：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `tasks` | 是 | 一批相互独立的任务；默认单轮最多 8 个，可按机器人配置，硬上限 16 个 |
| `tasks[].id` | 是 | 本批内唯一且稳定，用于匹配返回结果 |
| `tasks[].objective` | 是 | Worker 的明确目标，不应只是宽泛主题 |
| `tasks[].queries` | 否 | 主 Agent 已知的起始搜索词，Worker 仍可调整 |
| `tasks[].material` | 否 | 完成任务必需的背景材料，不传完整聊天历史 |
| `tasks[].source_policy` | 否 | `primary`、`balanced` 或 `community` |
| `max_concurrency` | 否 | 调用方期望并发数，只能向下收窄机器人配置，运行时还要应用全局上限 |

`source_policy` 只影响来源偏好，不能伪造来源质量：

- `primary`：优先官方文档、标准、论文和项目源代码；
- `balanced`：允许官方来源和可信二手来源互相补充；
- `community`：允许论坛、Issue 和真实使用反馈，但必须标注其性质。

### 现有接口兼容

现有调用继续有效：

```json
{
  "question": "材料中有哪些相互矛盾的地方？",
  "material": "……",
  "scope": "text"
}
```

运行时将其转换成只包含一个任务的内部请求。旧接口默认使用无工具轻量模式，避免已有摘要和抽取任务因为自动联网而改变语义、成本或延迟。

不建议继续保留含义不准确的 `scope=vision`。如果短期需要兼容，可以接受该值但返回清晰诊断；真正的视觉子任务应等输入协议能够携带图片后再开放。

### 模式选择

为了同时支持现有轻量推理和新增搜索，任务可以显式声明模式：

```json
{
  "id": "official",
  "mode": "search",
  "objective": "查找官方限制"
}
```

第一阶段只需要两种模式：

- `analyze`：无工具，处理调用方提供的材料；
- `search`：允许搜索和读取网页。

省略 `mode` 时：带 `queries` 的任务使用 `search`，只有 `material` 的任务使用 `analyze`。目标同时涉及材料和外部事实但未显式指定时，由调用方嘉然做出选择，工具内部不根据模糊文本猜测是否联网。

## 返回格式

批量结果必须与输入任务一一对应，并保持输入顺序：

```json
{
  "results": [
    {
      "id": "official",
      "status": "completed",
      "summary": "官方建议只对相互独立且边界明确的工作进行并行委派。",
      "findings": [
        {
          "claim": "并行 Worker 适合相互独立的调查方向。",
          "sources": [
            {
              "title": "来源标题",
              "url": "https://example.com/page",
              "kind": "primary"
            }
          ]
        }
      ],
      "unresolved": [],
      "usage": {
        "model_turns": 3,
        "tool_calls": 4,
        "duration_ms": 8200
      }
    }
  ]
}
```

`status` 至少支持：

- `completed`：在预算内得到可用结果；
- `partial`：有部分证据，但目标没有完全完成；
- `failed`：运行错误，结果不可用；
- `timed_out`：达到任务超时；
- `cancelled`：父调用取消或运行时关闭。

Worker 不应只返回自然语言长文。结构化的 `findings` 和 `sources` 能让嘉然去重、比较和引用，也方便测试来源是否真实存在。

## 并发与预算

建议的第一阶段默认值：

| 项目 | 默认值 | 硬上限建议 |
| --- | ---: | ---: |
| 单轮任务总数 | 8 | 16 |
| 单批并发数 | 3 | 4 |
| 每个 Search Worker 工具步骤 | 跟随 Agent 配置 | 跟随 Runner 全局安全上限 |
| 每个任务超时 | 分析 90 秒 / 搜索 180 秒 | 分析 90 秒 / 搜索 180 秒 |
| 单任务返回正文 | 分析 1,200 字符 / 搜索 4,000 字符 | 分析 1,200 字符 / 搜索 4,000 字符 |
| 委派深度 | 1 | 1 |

并发需要同时受三层约束：

1. 请求中的 `max_concurrency`；
2. 当前机器人的 `subtask_max_concurrency` 配置；
3. Runtime 全局模型并发闸门。

最终并发数取三者中的最小值。WebUI 在每台机器人的 Agent 配置中暴露 `subtask_max_tasks` 和 `subtask_max_concurrency`；调用参数不能抬高这两个预算，也不能绕过全局模型并发限制。

每个 Worker 独立计时和失败。父调用等待所有 Worker 结束，或在父上下文取消时统一取消仍在运行的 Worker。批内任务完成顺序不影响最终结果顺序。

## Worker 可用能力

第一阶段推荐只提供：

- Web 搜索；
- 打开和读取普通网页；
- 搜索结果规范化与来源账本；
- 必要的本地只读自省能力。

明确禁止：

- 文件写入、编辑和删除；
- 命令执行；
- 浏览器交互式点击、登录和提交表单；
- 修改机器人配置；
- 调用消息发送工具；
- 创建编码代理或后台任务；
- 调用 `subtask` 自身。

工具集合应在创建 Worker 时由运行时构造白名单，而不是把主 Agent 的完整 Registry 传入后依靠提示词要求模型不要使用。权限必须由代码保证。

## 上下文与提示词

Search Worker 默认不继承完整聊天历史。输入只包含：

1. 固定的只读搜索 Worker 系统规则；
2. 当前任务的 `objective`、`queries`、`material` 和来源策略；
3. 运行时提供的工具定义；
4. 当前 Worker 自己产生的搜索观察结果。

这样可以降低 Token 消耗，也避免把其他会话内容意外带到无关搜索中。

Worker 系统规则至少应明确：

- 只完成当前任务，不扩展为其他目标；
- 优先寻找能直接支持主张的来源；
- 不得把搜索摘要或结果标题当成已经打开验证的证据；
- 无法验证时返回 `partial`，不能补写看似合理的事实；
- 来源冲突时同时保留冲突，不替嘉然偷偷做最终裁决；
- 达到预算后立即整理已有证据，不重复相同查询。

## 失败处理

批量调度必须允许部分成功。例如三个 Worker 中一个超时，返回结果仍应包含另外两个已完成任务和超时任务的状态。

适合在 Worker 内自动恢复的情况：

- 搜索无结果时放宽引号、括号或限定词；
- 单个网页打不开时尝试其他来源；
- 某个来源内容为空时回到搜索结果选择其他页面；
- 模型第一次返回不符合结果结构时进行一次协议修复。

不应自动恢复或扩大权限的情况：

- 需要登录才能访问；
- 需要执行脚本、下载未知文件或提交表单；
- 任务实际要求修改外部状态；
- 用户要求访问当前 Worker 没有获得的数据源。

这些情况返回 `partial` 或 `failed`，由嘉然决定是否向用户说明限制或采用其他已授权能力。

## 可观测性与用量

每个 Worker 应产生独立 Trace，并通过父 Trace ID 与本次 `subtask` 调用关联。至少记录：

- 批次 ID、任务 ID 和模式；
- 排队、启动和完成时间；
- 模型轮数和工具调用数；
- 实际使用的模型配置；
- Token 用量；
- 最终状态和公开错误摘要；
- 来源数量与去重后的 URL 数量。

用量继续归入 `subtask` purpose，同时增加任务 ID 维度。这样现有模型用量统计仍能覆盖所有子调用，又能分析一次并行调研实际放大了多少成本。

不在默认日志中记录完整网页正文、密钥、工具鉴权信息或用户未要求持久化的材料。

## 与现有能力的关系

### Agent Runner

Search Worker 应复用 Agent Runner 的多步模型—工具循环、预算、超时、协议修复和搜索证据机制，但使用单独构造的只读工具注册表和更小的步骤上限。

主 Runner 仍保持“每个规划步骤执行一个工具”的协议。并行发生在一次 `subtask` 工具执行内部，因此不会改变所有现有工具的执行语义。

### 后台子任务

现有后台任务适合 OCR、图片生成等耗时且需要稍后主动通知用户的工作。第一阶段的批量搜索仍采用同步父调用：嘉然等待这一批 Worker 完成，然后在当前回复中综合结果。

如果后续真实使用表明搜索经常超过单轮回复时限，可以复用后台任务的状态持久化、取消和进度通知机制，但不应在第一阶段同时引入异步续答。

### 编码代理

编码代理继续负责需要读取完整项目、修改文件、运行测试或提交代码的任务。Search Worker 不获得这些权限。嘉然可以先用并行搜索 Worker 调查方案，再把已经收敛的实施目标交给一个编码代理。

## 嘉然的拆分策略

并行不应成为默认动作。以下情况适合拆成多个搜索任务：

- 可以从官方文档、实现案例和社区反馈等相互独立的角度调查；
- 需要比较三个以上候选方案；
- 多个来源可以并行收集，最后统一综合；
- 单一搜索方向容易遗漏重要证据。

以下情况应由嘉然直接处理或只创建一个任务：

- 用户问题简单且一个权威来源即可回答；
- 后续步骤严格依赖前一步结果；
- 多个任务会修改同一个状态；
- 拆分后的协调成本明显高于搜索本身；
- 用户只要求解释已经提供的材料。

第一阶段由嘉然显式生成任务组，不增加单独的“自动规划模型”调用。后续应根据真实数据评估是否值得把任务拆分也交给专门规划器。

## 实施计划

### 阶段一：接口与真正并发

- 为 `subtask` 增加 `tasks[]`、`mode` 和 `max_concurrency`；
- 保持旧单任务 schema 兼容；
- 增加批内任务校验、稳定排序和部分失败返回；
- 使用受控 goroutine 并发执行任务；
- 复用 Runtime 已有的模型并发信号量；
- 补充竞态、取消、超时和并发上限测试。

这一阶段可以先让 `analyze` 任务并行，验证调度器本身。

### 阶段二：只读 Search Worker

- 为 Worker 创建独立 Agent Runner；
- 构造只包含搜索和网页读取能力的 Registry；
- 工具步骤跟随现有 Agent 配置，不为 `subtask` 另设更低上限；保留工具输出和超时限制；
- 增加结构化结果协议与修复逻辑；
- 把模型调用记入 `subtask` purpose；
- 验证来源 URL、搜索证据和最终主张能正确关联。

### 阶段三：模型配置与前端

- 在模型分工中提供“子任务”或“搜索 Worker”配置项；
- 默认继续回退到聊天模型，避免升级后必须重新配置；
- 在调试视图展示批次、各 Worker 状态、耗时和用量；
- 根据使用数据决定是否需要单独的搜索模型档位。

### 阶段四：评测后再扩展

完成真实任务评测后，再考虑：

- 异步搜索任务；
- 中途追加要求或取消单个 Worker；
- 搜索产物缓存；
- 针对仓库、论文或特定 MCP 数据源的只读 Worker；
- 更通用的委派任务协议。

不建议在没有评测数据前开放递归委派和写入能力。

## 测试与验收

### 单元测试

- 旧单任务调用结果保持兼容；
- 批量任务输入顺序与输出顺序一致；
- 实际峰值并发不超过请求和全局上限；
- 一个任务失败不会取消其他任务；
- 父上下文取消后所有子任务都能退出；
- Worker 无法取得写入、命令和消息工具；
- 超长目标、材料、查询和返回内容均被明确限制；
- 重复任务 ID、空目标和超过任务数量上限会被拒绝；
- 所有模型用量都标记为 `subtask`。

### 集成场景

至少覆盖：

1. 同时调查一个框架的官方限制、实现案例和社区反馈；
2. 三个候选方案的并行比较；
3. 一个来源打不开但其他任务正常完成；
4. 搜索无结果后自动调整查询；
5. 用户取消当前回复时终止整批任务；
6. 全局模型并发已经被后台任务占用时正确排队。

### 推荐验收指标

- 对适合并行的多来源调查，结果覆盖率不低于主 Agent 串行搜索；
- 相比等量串行搜索，端到端耗时有明显下降；
- 简单问题不会被无意义拆分；
- 所有可引用主张都有对应来源 URL；
- Worker 不能产生任何写入或外部消息副作用；
- 并发和 Token 放大能够在运行日志中准确解释。

性能目标和成本阈值应在基准测试后确定，不在实现前假设固定百分比。

## 后续通用 Agent 方向

这项改造是嘉然成为通用 Agent 的第一块委派能力，但不等于立刻把所有任务都交给子 Agent。通用 Agent 的关键也不是“拥有尽可能多的工具”，而是能稳定完成下面的闭环：

```text
理解目标 → 制定计划 → 选择能力 → 执行与观察
    ↑                              ↓
交付结果 ← 汇总和验证 ← 失败恢复与重新规划
```

嘉然已经具备主 Agent Runner、工具系统、记忆、后台任务和编码代理。主要缺口是这些能力还没有统一在一个可委派、可观察、可恢复的任务控制面下。

### 通用 Agent 的目标模型

建议采用 Root Agent 加受限 Worker 的 manager 模式：嘉然始终拥有对话和最终回答，其他 Agent 作为工具接受边界明确的任务。它比直接把整段对话移交给另一个 Agent 更符合嘉然的人格连续性和现有权限模型。

长期分工如下：

| 能力 | 执行者 |
| --- | --- |
| 对话理解、规划、权限和最终回复 | 嘉然 Root Agent |
| 材料摘要、抽取和分类 | `subtask` analyze Worker |
| 多来源资料调查 | `subtask` Search Worker |
| OCR、生成图片等耗时插件操作 | 后台任务 |
| 修改项目、运行测试和提交代码 | 编码代理 |

后续如果需要增加可写的通用 Worker，应设计新的委派任务能力，而不是把写权限直接加入 Search Worker。这样可以保持搜索并行、安全边界和嘉然人格连续性，同时逐步扩展通用执行能力。

### 从工具调用升级为统一任务协议

通用 Agent 不能让每类后台能力拥有一套互不兼容的任务结构。搜索 Worker、后台插件和编码代理可以继续使用各自执行器，但控制面应逐步统一成一个 `Task`：

```json
{
  "id": "task-123",
  "parent_id": "turn-456",
  "kind": "search",
  "objective": "调查三个实现方案并比较风险",
  "inputs": [],
  "capabilities": ["web_search", "web_read"],
  "output_contract": "research_result_v1",
  "limits": {
    "max_steps": 6,
    "timeout_seconds": 180,
    "max_children": 0
  },
  "authority": {
    "read": true,
    "write": false,
    "external_action": false
  }
}
```

统一的是任务身份、父子关系、状态、权限、预算、产物和 Trace，不要求所有执行器使用相同实现。这样可以在不推翻现有后台任务和编码代理的前提下，让嘉然用同一种方式管理它们。

任务状态建议统一为：

```text
queued → running → waiting_input → completed
                  ↘ failed
                  ↘ timed_out
                  ↘ cancelled
```

第一阶段 Search Worker 不进入 `waiting_input`，缺少信息时返回 `partial`。等通用任务控制面支持恢复执行后，再允许嘉然或用户向运行中的任务补充信息。

### Root Agent 需要的协作原语

搜索批处理稳定后，可以把内部协作能力抽象为五个原语：

| 原语 | 用途 |
| --- | --- |
| `spawn_task` | 创建一个或一批受限任务 |
| `task_status` | 查询状态、阶段进度和部分产物 |
| `wait_task` | 等待一个或多个任务完成或需要处理 |
| `steer_task` | 对已有任务补充信息、收窄目标或纠正方向 |
| `cancel_task` | 取消不再需要或已经跑偏的任务 |

`subtask(tasks[])` 可以先作为 `spawn + wait` 的同步快捷方式：一次调用创建多个短任务并等待全部返回。后续的长任务再使用完整生命周期原语。这样能够先解决并行搜索，不必第一期就把任务系统全部重写。

### 能力配置而不是无限制工具继承

通用 Worker 不应自动继承 Root Agent 的全部工具。每个任务在启动时选择一个能力配置：

| 配置 | 可用能力 | 典型任务 |
| --- | --- | --- |
| `analyze` | 纯模型推理 | 摘要、抽取、分类 |
| `research` | 搜索、网页读取、只读数据源 | 调研、对比、事实核验 |
| `workspace_read` | 文件检索和读取 | 仓库探索、日志排查 |
| `execute` | 经过授权的文件写入和命令 | 小型本地执行任务 |
| `coding` | 隔离工作区中的编码代理 | 实现、测试、提交 |

能力配置应映射到运行时代码构造的工具白名单，而不是只写进提示词。任务材料、历史记录或 Worker 自己的输出都不能扩大权限。

最初只实现 `analyze` 和 `research`。`workspace_read` 可以在任务协议稳定后加入；`execute` 和 `coding` 必须结合审批、隔离工作区和单写者约束。

### 上下文应显式打包

通用 Agent 常见的失败来源之一，是把完整主对话无差别复制给所有 Worker。嘉然应为每个任务生成最小上下文包：

```json
{
  "objective": "当前任务目标",
  "constraints": ["不能修改外部状态"],
  "known_facts": ["主 Agent 已确认的事实"],
  "references": ["文件、网页或产物引用"],
  "expected_output": "需要返回的结构"
}
```

默认不传人格提示词、无关聊天历史、其他 Worker 的全部原始输出或 Root Agent 的内部推理。Worker 需要共享的长内容应保存为产物并传引用，避免每次复制正文。

对于连续任务，优先传上一次任务的结构化结果和产物引用，不直接恢复整个模型上下文。只有确实需要持续探索时，才保存 Worker 自己的会话状态。

### 产物应独立于聊天消息

通用任务的结果不只有一段文本。建议逐步引入统一 Artifact：

- 调研报告；
- 来源集合；
- 提取出的结构化数据；
- 文件补丁；
- 测试报告；
- 图片、文档和其他生成文件；
- 失败诊断与可恢复检查点。

任务结果只返回摘要和 Artifact ID，Root Agent 根据需要读取。这样可以减少主对话上下文占用，也允许后台任务、编码代理和搜索 Worker 使用同一套结果回流方式。

### 规划应由模型决定，约束应由代码执行

嘉然可以根据问题动态决定：

- 是否需要委派；
- 拆成几个任务；
- 哪些任务可以并行；
- 结果不足时是否继续调查；
- 哪个执行器最合适。

但以下事项必须由运行时代码控制：

- 最大并发数和任务总数；
- 最大层级、模型轮数、工具步数和超时；
- 工具和数据访问权限；
- 是否允许写入或对外产生动作；
- 同一资源的写入冲突；
- 取消、关闭和进程退出时的清理；
- 用量、Trace 和审计记录。

简言之，模型负责选择路线，运行时负责划定道路边界。

### 重新规划与结果验证

只有“创建 Worker 并收集答案”还不算通用 Agent。Root Agent 需要能根据结果重新规划：

1. 检查任务是否真正回答了目标；
2. 检查来源、文件或测试证据是否存在；
3. 识别多个 Worker 之间的冲突；
4. 对缺口创建补充任务，或对原任务进行 `steer`；
5. 在预算耗尽时说明未完成部分，而不是继续无限委派；
6. 汇总成符合用户意图的最终结果。

对于高风险动作，可以增加专门的验证阶段，但不建议默认再创建一个“审核 Agent”。优先使用确定性的验证，例如 schema 校验、文件存在性、测试命令退出码、来源 URL 和 Git diff；只有语义判断确实需要时才调用模型审核。

### 写入能力必须最后开放

Search Worker 只读时，并发冲突很小。进入通用执行阶段后，必须增加以下边界：

- 一个工作区同一时刻只允许一个写入任务；
- 并行编码任务使用独立 worktree 或沙箱；
- 外部消息、发布、删除和配置修改继续沿用主人权限与审批；
- Worker 不能因为任务文本中出现“用户已同意”就获得授权；
- 可恢复操作优先，重要写入保留 diff、备份或提交；
- Root Agent 在交付前检查任务产生的实际变更，而不是只相信 Worker 摘要。

这也是不应把写权限直接加入 `subtask search` 的主要原因。

### 建议的能力阶梯

#### L1：并行只读调查

- `subtask(tasks[])`；
- `analyze` 与 `search`；
- 独立上下文、结构化结果、来源证据；
- 最大并发 3，委派深度 1。

这是当前设计要实现的阶段。

#### L2：持久任务控制面

- 统一 Task ID、状态和父子 Trace；
- `spawn/status/wait/cancel`；
- 任务结果和 Artifact 存储；
- 断线、进程重启或长耗时任务的状态恢复；
- 前端展示任务树和资源消耗。

这一阶段让嘉然能够可靠管理超过单轮回复时间的工作。

#### L3：可纠偏的 Worker

- `steer_task` 和 `waiting_input`；
- Root Agent 根据阶段结果追加条件；
- 复用 Worker 或启动补充任务；
- 任务级会话状态和检查点；
- 明确的总预算与停止条件。

这一阶段让嘉然从“一次派活”升级为真正的持续协调者。

#### L4：受控执行 Agent

- `workspace_read` 和受限 `execute` 能力；
- 审批、能力令牌、沙箱和单写者锁；
- 编码代理接入统一任务协议；
- 变更、测试和外部动作的确定性验证；
- 失败后的回滚或可恢复检查点。

这一阶段才开始具备通用执行能力。

#### L5：自适应调度

- 根据任务类型、复杂度和历史效果决定是否委派；
- 为 Root Agent 和 Worker 选择不同模型；
- 在质量、延迟和成本之间动态调整任务数；
- 根据评测数据优化拆分策略；
- 在安全上限内开放有限的二级委派。

只有 L1 至 L4 的评测和运行数据稳定后，才应考虑递归 Agent。

### 通用 Agent 的验收标准

不能以“能启动多个 Agent”作为完成标准。至少应分别评估：

| 维度 | 关注指标 |
| --- | --- |
| 完成质量 | 目标完成率、证据覆盖率、测试通过率 |
| 调度质量 | 是否只在适合时拆分、任务是否相互独立、重复工作比例 |
| 性能 | 端到端耗时、排队时间、并行利用率 |
| 成本 | 主 Agent 与所有 Worker 的总 Token 和工具调用 |
| 安全 | 越权调用、未经批准的写入或外部动作数量 |
| 恢复能力 | 超时、部分失败、取消和重启后的行为 |
| 可解释性 | 能否说明每个任务为什么创建、做了什么、产出什么 |

简单任务应继续由单个嘉然完成。多 Agent 的收益主要来自边界清楚、可以并行、需要独立上下文的复杂工作；有严格顺序依赖或共享可变状态的任务通常更适合一个 Agent 连续执行。

### Pi Agent 对照与吸收

Pi 的设计对嘉然很有参考价值，但应区分三个层次：

1. `pi-agent-core` 是有状态的 Agent loop；
2. `pi-subagent` 是建立在 Pi 扩展机制上的持久子 Agent；
3. `pi-durable` 是更底层的持久会话、任务和文档运行时。

Pi 核心刻意保持最小化，默认不内置 subagent，而是允许通过扩展实现不同编排方式。嘉然不必复制这种产品形态，但值得借鉴“核心循环稳定、编排能力建立在明确接口之上”的分层。

#### Agent loop

Pi Agent Core 提供的关键能力包括：

- Agent 状态与事件流；
- 每轮调用前的上下文转换和压缩；
- 工具调用的并行或顺序执行模式；
- 工具调用前后的拦截钩子；
- `steer` 和 `followUp` 两类消息队列；
- `abort` 与 `waitForIdle`；
- 可动态调整的模型、工具和思考预算。

嘉然现有 Runner 已经覆盖多步工具循环、预算、超时、延迟工具和 Observer，但缺少两类通用能力：

1. 运行中的控制消息队列；
2. 同一模型响应内多个安全工具调用的并行执行。

对 Search Worker 而言，第一阶段不必先修改主 Runner 的工具并行语义，因为任务并发由 `subtask(tasks[])` 提供。但 Worker 稳定后，可以考虑为明确声明为只读、互不冲突的工具加入并行执行模式。写工具继续保持顺序执行。

`steer` 和 `followUp` 应保持语义区别：

- `steer`：当前任务方向有误，在下一轮尽快注入纠正信息；
- `followUp`：当前目标完成后继续做另一项相关工作。

这比把所有追加消息都解释成普通聊天更容易控制长任务。

#### 持久子 Agent

Pi Subagent 使用稳定句柄管理独立子会话，提供 `spawn`、`status`、`send`、`follow-up`、`wait`、`stop` 和 `list`。每个子 Agent 拥有独立会话，可以限制工具，并且默认禁止嵌套创建更多子 Agent。

这与嘉然规划中的任务原语高度一致。建议据此调整命名和语义：

| 嘉然能力 | Pi 对应能力 | 说明 |
| --- | --- | --- |
| `spawn_task` | `spawn` | 创建任务并返回稳定 Task ID |
| `task_status` | `status` / `list` | 查询单个或全部任务 |
| `steer_task` | `send` | 修正运行中的任务 |
| `followup_task` | `send --follow-up` | 当前工作结束后追加任务 |
| `wait_task` | `wait` | 等待状态发生变化或结束 |
| `cancel_task` | `stop` | 取消运行并完成资源清理 |

原设计中的五个原语应增加 `followup_task` 和 `list_tasks`，避免以后用一个含义模糊的接口同时承担纠偏、续做和枚举。

Pi Subagent 通过 tmux 和独立 JSONL 会话实现持久性，这适合本地终端 Agent；嘉然是长期运行的服务，不应引入 tmux 作为任务基础设施。应复用现有数据库、事件子任务记录、Runtime 并发闸门和服务生命周期，在进程内执行 Worker，并把状态持久化到现有存储。

#### Durable task runtime

Pi Durable 更值得嘉然中长期参考。它的核心原则是：会话消息、模型轮次、工具调用和应用状态在对外可见前先提交到存储；任务每一步保存检查点，进程重启后从最后一个已提交状态继续。

其中值得吸收的设计包括：

- 每个任务有明确 owner，可以属于会话或另一个任务；
- generation 任务拥有本轮 tool tasks，并等待它们完成；
- 所有状态通过原子 commit 更新；
- 重复 `requestId` 返回原有任务，避免重试造成重复执行；
- 工具声明自己的 replay policy；
- 结构化输出与给模型看的文本输出分离；
- 嵌套工具调用保留 parent task 和 parent call；
- 模型可见工具与内部可调用工具分开控制；
- 进程崩溃后，安全任务可以恢复，不安全动作得到 interrupted 结果。

嘉然的统一 Task 协议应相应补充：

```json
{
  "id": "task-123",
  "request_id": "由调用方提供的幂等键",
  "owner_id": "turn-456 或 parent-task-789",
  "parent_call_id": "可选的父工具调用",
  "replay_policy": "safe | interrupt | abandon",
  "output": "提供给 Root Agent 的有界文本",
  "structured_output": {},
  "details": {},
  "checkpoint": {}
}
```

三个输出通道分别服务不同消费者：

- `output`：给模型看的精简结果；
- `structured_output`：供嘉然运行时、任务编排器和测试读取；
- `details`：供前端展示进度、来源、日志和诊断。

这比让所有消费者解析同一段自然语言更可靠。

#### 不直接照搬的部分

Pi 的部分选择不适合原样迁移：

- Pi 默认继承启动进程的系统权限，嘉然必须继续使用已有身份、关系和工具权限控制；
- Pi Subagent 的 tmux 隔离不适合服务端多平台部署；
- Search Worker 不需要完整终端 TUI 和独立工作目录；
- 第一阶段不需要允许 Worker 安装任意扩展或 Skills；
- 通用搜索不应获得 Pi 编码 Agent 默认的 `write`、`edit` 和 `bash`；
- Pi Durable 当前仍标记为实验性，概念可以借鉴，接口不应直接成为嘉然的兼容目标。

因此，推荐吸收 Pi 的生命周期和状态模型，而不是把 Pi 作为子进程嵌入嘉然或复刻它的终端运行方式。

#### 对当前方案的具体修正

参考 Pi 后，当前路线作以下修正：

1. `subtask(tasks[])` 的每个任务从第一版就分配稳定 Task ID 和 owner；
2. 返回值从单段文本升级为 `output + structured_output + details`；
3. 批量调用增加 `request_id`，网络或模型重试不能重复创建同一批任务；
4. 为任务预留 `replay_policy`，搜索默认 `safe`，外部写操作默认 `interrupt`；
5. 通用任务原语补充 `followup_task` 和 `list_tasks`；
6. `steer` 与 `follow-up` 分成两条队列；
7. 父任务取消时传播到子任务，但单纯取消 `wait` 不等于取消任务本身；
8. 嵌套任务第一阶段仍禁用，但数据结构保留 owner 和 parent 字段；
9. 先持久化任务状态，再向 UI 或 Root Agent 报告完成；
10. 后续只有声明为只读且无冲突的工具才允许同轮并行执行。

### 推荐实施顺序

结合当前代码基础，推荐顺序是：

1. 完成本设计中的并行 Search Worker；
2. 抽取统一 Task 元数据和父子 Trace，不立即统一所有执行器代码；
3. 为长任务增加 `status/wait/cancel` 和 Artifact；
4. 增加 `steer`、检查点和恢复执行；
5. 将编码代理映射到统一 Task 控制面；
6. 最后增加受控的通用执行 Worker 和自适应调度。

这条路线保留现有实现，先让嘉然获得最有价值的并行调查能力，再逐步补齐通用 Agent 真正需要的任务生命周期，而不是一次性重写 Agent Runtime。
