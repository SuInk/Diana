# 能力知识库

`capabilities` 工具回答两类问题：「你会不会做某事」和「某个功能怎么运作、为什么这样」。两类问题各走一条检索道，结果分开返回。

## 两条检索道

**items：能力条目。** 内容是手写的核心能力条目（`coreCapabilityDocuments`）、当前平台的消息格式规则，以及实时插件清单（插件是否安装、是否启用、需要什么权限）。每条只有一两句话，回答「会不会」「归哪个插件」「要什么关系等级」。

**references：参考资料。** 内容有四种来源，每条带 `source` 字段：

| source | 内容 | 来源 |
| --- | --- | --- |
| `doc` | 设计文档，按标题切成章节 | `docs/*.md` 和中文站点的配置、实现、运维三页，随程序编译 |
| `prompt` | 内置提示词的用途和默认原文 | 提示词登记表（`PromptSpecs`） |
| `tool` | 工具说明和参数 | 本轮注册表里实际挂上的工具 |
| `skill` | Skill 的用途说明 | 本轮注册表里的 Skill 目录 |

两条道分开排序。文档一节动辄上千字，和一句话的能力条目放在一起打分，能力条目会被挤出前几名，「你会什么」这类问题就答偏了。

## 为什么文档要编译进程序

文档通过 `docs/embed.go` 用 `go:embed` 编进二进制，所以检索到的永远是和这份程序同一次提交的文档。直接去 GitHub 读 main 分支，拿到的可能是更新的写法，用它解释线上还在跑的旧版本会答错。返回结果里的 `knowledge_version` 是这份文档对应的源码基线版本号。

英文站点（`docs/en/`）和站点自身的 `README.md` 不收录：前者和中文页内容重复，后者讲的是怎么发布文档站，不讲 Diana 的行为。

## 工具说明取本轮注册表

工具和 Skill 条目不在启动时固定，而是取本轮注册表里的那一份。平台、权限和插件开关已经在注册表里筛过，所以模型检索到的正是它这一轮能调用的工具；非主人检索不到主人专属工具，Telegram 上也检索不到仅 OneBot 可用的工具。

## 提示词只说默认值

人设可以逐段改写内置提示词（见 [内置提示词覆盖](prompt-overrides.md)）。知识库收录的是登记表里的默认原文，工具返回的说明会要求模型只能说「默认是这样」，不能说成这台机器人当前实际使用的版本。

## 检索

检索只在本地进行，不调用 embedding 服务。切词方式和能力条目相同：ASCII 词，加汉字的单字、二字和三字片段。参考资料一侧用 BM25 打分，章节标题按三倍权重计。

查询里的疑问词会先去掉：「为什么」「怎么」「是不是」这类短语，以及「吗」「呢」「的」「是」等几乎不构词的单字。「会」「能」不在去除之列，否则「会话」「能力」会被拆坏。之所以要去疑问词，是因为不少文档标题本身就是问句（「实时画面是怎么来的」），不去掉的话，「记忆是怎么召回的」会先命中浏览器文档。

默认返回 3 条摘录，每条约 420 字，从命中最密的段落开始截，而不是一律从章节开头截。带 `detail=true` 时返回最多 6 条完整章节，每条不超过 1500 字。得分低于第一名 35% 的结果直接丢弃，避免零散单字命中占用上下文。

静态语料（文档和提示词）在第一次检索时建索引，约 40 毫秒，之后每次检索约 1 毫秒。
