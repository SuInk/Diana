# 插件消息出口

插件发进聊天的消息分两类，走两条不同的出口。分不清这件事，就会出现"把错误提示关了，
仓库订阅的失败告警照样进群"，或者"机器人停用了，它的订阅还在抓 GitHub 并报错"。

## 两类消息

| | 内容 | 诊断 |
| --- | --- | --- |
| 是什么 | 用户订阅或触发的东西本身 | 系统状态：坏了、又好了 |
| 例子 | 提醒正文、RSS 与仓库更新、定时查询结果、后台任务结果与进度、插件的 `Reply` | 「仓库订阅连续 3 次失败」「订阅已恢复」「后台任务执行失败」 |
| 受开关控制 | 否 | 是 |
| 关掉开关后 | 照常发送 | 不发，但仍写入事件、`LastError` 和应用日志 |

判断标准只有一条：**这句话是用户要的东西，还是在向用户解释系统自身的状态。** 解释状态的
一律算诊断，包括"已恢复"——失败告警都没发出去过，再补一条"已恢复"只会让人莫名其妙。

## 两级开关

诊断消息要两个开关都开着才发出去：

| 开关 | 位置 | 管的范围 |
| --- | --- | --- |
| 机器人的「错误提示」 | 机器人设置，`ErrorNotifyEnabled` | 这台机器人的全部诊断消息 |
| 插件的「发送错误通知」 | 插件设置，`error_notice` | 这一个插件产生的诊断消息 |

机器人那个关掉，插件这个开着也不发——用户关掉「错误提示」是想让机器人别再因为自己的
毛病说话，插件不该有豁免。插件这个是给"某个订阅老是失败、但别的告警还想要"准备的。

RSS 订阅和仓库订阅另有一项 `failure_alert_threshold`（「连续失败几次才报」，默认 5，
1–100）：周期订阅连续失败到这个次数才发告警，恢复时再发一条。机器人的「错误提示」或插件
的 `error_notice` 关着时不计数也不告警（和发送出口用同一个 `diagnosticAllowed` 判断）；定时查询不属于任何插件，固定用默认值。

`error_notice` 不用各插件自己写进清单：插件在 `PluginManifest` 里标
`ReportsErrors: true`，`withErrorNoticeSetting` 会在注册时补上这一项（默认开）。
会经诊断出口说话的插件都要标上，不会报错的插件不标，插件页上就不会多出一个永远用不上
的开关。插件自己已经声明了同名设置项时不重复添加。

## 出口

诊断消息只有三个出口，都在 `model/assistant/diagnostic_notice.go`，共用同一处开关判断：

| 出口 | 用于 |
| --- | --- |
| `sendDiagnosticNotice(ctx, event, pluginID, text)` | 发给单个订阅者：提醒失败、周期订阅失败与恢复 |
| `sendDiagnosticNoticeWithEvidence(ctx, event, pluginID, text)` | 需要送达确认：仓库订阅按配置的多个通知目标逐个发，据此判断这次告警算不算发出去了 |
| `sendDiagnosticFollowup(ctx, event, pluginID, text)` | 后台任务（含第三方插件任务）跑挂了、结果发不出去 |

`pluginID` 是产生这条诊断的插件，用来读它的 `error_notice`。核心自己的诊断（例如普通
一次性提醒）传空串，只看机器人那个开关。提醒和后台任务分别用
`reminderDiagnosticPluginID`、`subagentTaskPluginID` 反查，不要在调用处硬写 ID。

内容消息继续用原来的 `sendSubscriberNotice`、`sendRepositoryWatch`、`sendSubagentFollowup`、
`sendOutgoing`，不受开关影响。

**新增诊断消息时不要自己判断开关**，直接用上面三个出口之一。以前是各插件各判一次，结果
只有回复出错那条路径真的认这个开关，其余全部绕过。

### 被开关挡下时返回 nil

三个出口在开关关闭时返回 `nil` 而不是错误。调用方据此照常记下「已告警」，否则每个周期都
会重新尝试发送一次，开关就只挡住了第一次。

## 什么时候根本不该跑

开关管的是"发不发"，下面两条管的是"跑不跑"，在更前面：

- **机器人停用**：停用机器人名下的提醒和订阅在认领阶段就跳过，既不请求外部服务，也不产生
  任何通知。重新启用后按原周期继续。判断用 `Runtime.disabledProfiles`，和入站那边同一份。
- **进程退出或停用途中**：在途请求会带着 `context.Canceled` 回来。那不是订阅坏了，不计入
  连续失败，排到下一个周期即可。任务自身的超时（`DeadlineExceeded`）仍然算失败。

## 第三方插件

第三方插件**没有直接的诊断通道，也不需要有**。它们只返回内容：

```jsonc
{
  "handled": true,
  "reply": "……",          // 内容，照常发送
  "image_urls": ["…"]
}
```

诊断由运行时统一产生和发送：

- 插件执行返回错误 → 运行时记应用日志（`plugin_execute`），按需要通过上面的诊断出口告诉
  用户，受「错误提示」开关控制。
- 插件注册的后台任务失败 → 走 `sendDiagnosticFollowup`，同样受开关控制。任务会带上提交
  它的插件 ID，因此读的是这个插件自己的 `error_notice`。

因此第三方插件作者需要注意：

1. **失败就返回错误，不要把错误写进 `reply`。** 写进 `reply` 的内容会被当成内容消息，绕过
   开关直接进聊天，用户关掉错误提示也挡不住——这是插件在替用户做决定。
2. **不要自己重试到底再报错。** 周期任务的重试、退避和"连续失败 N 次才告警"由运行时负责，
   插件只需要如实返回这一次的结果。
3. **区分"没有结果"和"失败"。** 没有新内容就返回 `handled: false` 或空 `reply`，不要返回
   一条"本次没有更新"的消息——那会变成每个周期一条内容消息。

4. **会报错就在清单里标 `"reports_errors": true`。** 标了之后插件页上会多出「发送错误通知」
   开关，用户可以单独关掉你这个插件的失败告警，而不必连整台机器人的错误提示一起关。

插件声明的 `message:send` 权限指的是发送**内容**。诊断消息不属于插件能力范围，插件无法绕过
开关，这是有意的。

## X 订阅配图

X（Twitter）订阅通过 FxTwitter 获取动态时，会保留 `media.photos` 中的图片供通知使用，
图片地址不进入 LLM 判断提示词。判断器仍只根据文字决定是否通知。

- 回复引用完整推文链接（兼容 `x.com` 和 `twitter.com` 的 status 地址），或唯一属于某条动态的正文链接时，附上该条动态的图片。
- 多条动态共用同一正文链接时，不凭该链接选择图片；没有明确引用的多条汇总不附图。只有一条新动态时，通知自动附上它的图片。
- 每条动态最多两张，每个来源的单次通知段落最多四张，同一段落内相同图片 URL 去重；多来源订阅分别计算。
- 只接受 HTTPS 的 `pbs.twimg.com` 地址，不接受用户名或显式端口。暂不处理视频、引用动态的媒体、网页卡片封面和普通 RSS/Atom 中的图片。

通知持久化时保留图片标记，发送时转换为各平台共用的图片字段；OneBot 和 Telegram
均有投递路径测试，其他平台使用各自已有的图片发送能力。图片发送失败仍按现有通知失败
机制上报和重试，不会静默标为成功。Telegram 先发送文字再发送图片，因此文字可能已送达；
整条通知重试时可能重复文字，与现有通知部分发送失败的边界一致。
