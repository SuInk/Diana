# GitHub 订阅游标

GitHub 订阅的五类动态分别维护检查点，不能用同一种字符串比较处理所有类型。

| 类型 | 前进依据 | 空响应或旧响应 |
| --- | --- | --- |
| Issue / PR | `updated_at`，同一时间再比较编号 | 保留已有水位；乱序数据取最大有效水位 |
| Commit | 提交祖先关系 | 保留旧 SHA；列表找不到旧 SHA 时通过 compare 核对，只接受 ahead 的新增提交范围 |
| Release | GitHub 发布时间，时间相同再比较 Release ID | 保留标签及时间/ID；不按版本字符串或列表首项判断新旧 |
| Star | WatchEvent 时间，时间相同再比较数字事件 ID | 保留事件 ID 和时间，不因列表空缺、乱序或窗口变化清零 |

## 兼容与边界

- 首次建立基线不推送历史。Issue/PR、Release、Star 首次为空后出现的第一条真正动态仍会通知；Commit 沿用原有要求，需要已有首个提交才能建立初始基线。
- 旧版仅保存 Release tag 的订阅会从列表或按 tag 查询补齐发布时间和 ID，并持久化。已经保存时间水位后，即使旧 Release 被删除，也能按水位识别后续发布。重建同名标签的 Release 以新记录的时间和 ID 判断，不混同旧发布。
- 旧 Release 无时间水位且原标签已无法查询时，保留检查点并报错，不猜测哪个版本更新。
- Commit 缺少旧 SHA 时，compare 无法确认 ahead、分支回退或历史分叉均不会触发历史补发。接口失败保留状态并按原机制重试。确认要跟随强推重写后的历史时，应显式重建订阅基线；不自动把最近一页旧提交当成新提交。
- Star 总数是统计值，可以因取消 Star 或缓存修正而下降；只要求事件水位不倒退。没有可验证时间或 ID 顺序的旧事件不会被猜成新增。
- 人为更换仓库、分支或重新启用监控项时，沿用显式建立新基线的行为；这与轮询异常造成的隐式回退不同。
- PR / Issue 的动态种类和 Release 的版本种类（正式版、预发布）只决定报不报，不影响游标：被过滤掉的记录照样让检查点前进，重新勾选后不会把期间攒下的旧记录一次性补推。草稿 Release 不进入通知，也不参与游标。

## 按用户屏蔽通知

在仓库订阅的「仓库通知 → 屏蔽用户的通知」填写 GitHub 用户名，多个用逗号分隔；单行输入框会识别 `@username`、GitHub 主页链接和 `dependabot[bot]`，并自动查询前 10 个账号的公开昵称，不区分大小写，最多 100 个。名单仅作用于这一条订阅；聊天工具 `github_watch` 的 `create/update` 也支持 `blocked_users` 数组，更新时省略保持原值，传 `[]` 清空。

- Issue / PR 按创建者过滤整条动态，包括后续更新、关闭、重新打开或合并；不是按最后评论者判断。
- Commit 按 GitHub 关联的作者账号过滤，PR 内的提交清单也过滤；没有关联账号时不把 Git 作者显示名当用户名猜测。
- Release 按发布者过滤；Star 按点星事件的操作者过滤。
- 被屏蔽的事件仍推进游标，解除屏蔽后不补发旧动态。名单变更会清除旧的待投递内容，并拒绝保存使用旧名单产生的轮询结果。
- Star 的实际总数不变；被屏蔽的新增事件不计入增长通知阈值，只有被屏蔽事件时不通知。里程碑仍按仓库实际总数判断，但至少存在未屏蔽的新点星事件才通知。
- 摘要和自动跟评使用过滤后的清单；配置屏蔽名单时不附带可能混入被屏蔽提交的聚合 diff。名单只控制通知，不影响主动查询 GitHub 或仓库管理权限。

## 评论正文与原通知引用

- 被选中的 Issue / PR 动态会读取上次水位之后新增或编辑的评论，展示作者、时间、当前正文和评论直达链接；PR 同时读取普通讨论和代码审查行内评论。编辑评论显示修改后的正文，不提供修改前后的差异。
- 每个条目的评论展示数量沿用「每类动态展示条数」，单条正文最多 1500 字；每种评论接口最多读取 5 页、每页 100 条，达到抓取或展示上限时提示查看原文。首次建立订阅基线不补发旧评论。
- 评论接口失败时整轮保留旧游标，下次重试，避免跳过正文。评论仍随父 Issue / PR 的动态筛选触发；未选中的父动态、删除评论和没有引起父记录更新时间变化的事件，不单独通知。
- 评论作者也按屏蔽名单过滤；私有仓库打码时去掉评论作者和直达链接，正文仍按现有通知规则展示。
- 同一 Issue / PR 后续通知引用该投递目标中首次通知的消息 ID。引用使用订阅保存的锚点，不依赖短期聊天历史或模型引用标记；失败补投保留关联编号。没有锚点时正常发送，并在成功后记录供以后引用。

## 保存与日志

抓取结果带上它读取的原检查点。保存前再次核对来源、监控类型及各游标；已经过期的结果会被丢弃，不能覆盖新游标或新的待发送内容。合法的待投递通知仍按原重试机制处理。

日志记录被保留的旧游标、收到的候选值和保留原因，以及成功保存前后的各类游标，不记录 Token 或通知正文。
