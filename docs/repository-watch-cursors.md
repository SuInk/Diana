# GitHub 订阅游标

GitHub 订阅的五类动态分别维护检查点，不能用同一种字符串比较处理所有类型。

| 类型 | 前进依据 | 空响应或旧响应 |
| --- | --- | --- |
| Issue / PR | `updated_at`，同一时间再比较编号 | 保留已有水位；乱序数据取最大有效水位 |
| Commit | 提交祖先关系 | 保留旧 SHA；列表找不到旧 SHA 时通过 compare 核对，只接受 ahead 的新增提交范围 |
| Release | GitHub 发布时间，时间相同再比较 Release ID | 保留标签及时间/ID；不按版本字符串或列表首项判断新旧 |
| Star | WatchEvent 时间，时间相同再比较数字事件 ID | 保留事件 ID 和时间，不因列表空缺、乱序或窗口变化清零 |

## 兼容与边界

- 首次建立基线不推送历史。Issue/PR、Release、Star 首次为空后出现的第一条真正动态仍会通知；Commit 沿用原有要求，需要已有首个提交才能建立初始基线。
- 旧版仅保存 Release tag 的订阅会从列表或按 tag 查询补齐发布时间和 ID，并持久化。已经保存时间水位后，即使旧 Release 被删除，也能按水位识别后续发布。重建同名标签的 Release 以新记录的时间和 ID 判断，不混同旧发布。
- 旧 Release 无时间水位且原标签已无法查询时，保留检查点并报错，不猜测哪个版本更新。
- Commit 缺少旧 SHA 时，compare 无法确认 ahead、分支回退或历史分叉均不会触发历史补发。接口失败保留状态并按原机制重试。确认要跟随强推重写后的历史时，应显式重建订阅基线；不自动把最近一页旧提交当成新提交。
- Star 总数是统计值，可以因取消 Star 或缓存修正而下降；只要求事件水位不倒退。没有可验证时间或 ID 顺序的旧事件不会被猜成新增。
- 人为更换仓库、分支或重新启用监控项时，沿用显式建立新基线的行为；这与轮询异常造成的隐式回退不同。

## 保存与日志

抓取结果带上它读取的原检查点。保存前再次核对来源、监控类型及各游标；已经过期的结果会被丢弃，不能覆盖新游标或新的待发送内容。合法的待投递通知仍按原重试机制处理。

日志记录被保留的旧游标、收到的候选值和保留原因，以及成功保存前后的各类游标，不记录 Token 或通知正文。
