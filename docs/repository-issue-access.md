# Issue 授权：按人、按群，以及群身份要求

`github` 工具的管理人员授权按用户或按群配置。创建、更新、评论、review、关闭和重新打开等写入仍需仓库白名单、有效 GitHub 凭据以及用户确认码。

## 按用户：管理人员跨会话生效

`issue_manager_user_access`（含旧版 `user_repository_access` 回落）按 `用户 ID = owner/repo, owner/repo` 填写。该用户在私聊和群聊中都可以读取、发起写操作及确认对应仓库的草稿，不要求另有群管理员身份，也无需重复授予整个群权限。群聊中的结果会展示给当前群。

单独的 `issue_draft_user_access` 草稿提交授权和 `code_reader_user_access` 源码读取授权仍只在私聊生效，不获得管理人员的跨会话权限。

## 群里的草稿谁来批

机器人主人、该仓库的授权管理人员，以及本群额外配置的草稿审批人可以确认草稿。所有写入都必须经过现有确认码流程；管理人员授权不会跳过确认。

`issue_approver_group_access` 按 `群 ID = 用户 ID, 用户 ID` 填写。额外审批人只可确认本群草稿范围内的仓库，不因此获得其他仓库权限。个人管理人员和审批人仍需个人 Token 或显式配置的认证来源，凭据本身也必须有 GitHub 写入权限。

## 按群：整群授权，可以再限定群身份

`issue_manager_group_access`、`issue_draft_group_access`（老字段 `group_repository_access`）按 `群 ID = owner/repo, owner/repo` 填写，授权范围是该群成员。

默认群里所有人都算数——这是老行为，不写后缀的配置读进来语义不变。要收窄就在仓库后面加身份要求：

| 写法 | 谁能用 |
| --- | --- |
| `owner/repo` | 群里所有成员 |
| `owner/repo#group_admin` | 群主和群管理员 |
| `owner/repo#group_owner` | 只有群主 |

机器人主人在哪一档都通行：主人的权限本来就不经过这份名单。

## 两个"管理"不是一回事

- **Issue 管理人员**：Diana 这个插件的授权角色，决定谁能直接写 GitHub、谁负责确认草稿。由上面那几项名单决定。
- **群主 / 群管理员 / 群成员**：聊天平台给的群内身份，由平台决定，Diana 只是读。`#group_admin` 这类后缀说的是它。

一条按群授权写成 `#group_admin`，意思是"这个群里，群主和群管理员算作 Issue 管理人员"，不是"群管理员就是 Issue 管理人员"。想授予个人跨会话读写权限，用按用户的管理人员授权；只允许确认本群草稿时，用「群聊草稿审批人（按群）」。

管理人员自动也是草稿人（`repositoryPublishEffectiveAccess` 里显式合并），不必重复添加。两条授权覆盖同一个群 + 仓库时，草稿侧按更宽的那条算——否则把管理人员收窄到群管理员，会连带把本来放给全体成员的草稿权一起收走。

## 身份怎么取，取不到怎么办

先看事件自带的 `SenderRole`（OneBot 每条群消息都带 `sender.role`，Telegram 的 `creator`/`administrator`、钉钉的 isAdmin 都由 `NormalizeGroupRole` 收敛成同一套取值），拿不到再回查一次群成员信息。

查不到身份时按最严处理：除「所有成员」外一律拒绝，并在回复里说明是平台没提供群身份，而不是仓库没配。身份够不上时同样明确拒绝，提示里写清这条授权要求什么身份、当前身份是什么，以及"想在本群单独放行某个人，用「群聊草稿审批人（按群）」"。

身份查询是惰性的：一条带后缀的授权都没有时，不会为此多打任何平台接口。`subscription`（kind=github）的管理清单属于每条消息都要走的热路径，那里只认事件自带的身份，不额外回查。

## GitHub Star

GitHub 插件中的“允许 GitHub Star”默认关闭，在控制台开启时需要二次确认。启用后仅机器人主人能提出 `github(operation="star", repository="owner/repo")`；生成的草稿会展示仓库和账号来源，由主人在新的聊天消息中原样回复确认码后实际发送幂等的 Star 请求；已登录控制台的管理者也可核对草稿后直接提交。仅传 `user_confirmed_write=true` 不能越过确认码。定时任务也不能自行确认写入。关闭开关后，已有 Star 草稿也不能提交；Agent 安全模式会拦截 Star。

Star 使用目标仓库绑定的凭据，未绑定时使用公共 Token 或 gh 登录账号；因此这是给配置的账号点 Star，并不是替群友个人账号操作。Fine-grained Token 需要账号级 `Starring: write` 权限；GitHub App 安装凭据不能用于 Star。Issue 管理、群管理员或仓库白名单授权都不授予 Star 权限。不会取消 Star，也不会开启 Watch 通知。

### 群聊中读取私有仓库

机器人主人和该仓库的授权管理人员可以在群聊中查看私有仓库信息、Issue、PR 和源码。按用户的管理人员名单（含旧版用户仓库授权回落）在此读取场景生效，仍需个人 Token 或显式配置的认证来源；按群的管理人员授权继续遵守配置的群身份要求。结果会发送到当前群，群成员均可看到。只有群管理员身份、草稿提交权限或单独的私有源码读取授权，不足以在群聊中读取私有仓库。公开仓库读取规则不变；管理人员写入跨会话生效，仍受白名单、凭据和确认码约束。
