# Issue 授权：按人、按群，以及群身份要求

`github` 工具的写操作（create / update / comment / review / close / reopen）看两件事：在哪种会话里，以及哪份授权名单覆盖了你。私聊只认「按用户」，群聊只认「按群」，两边不越界。

## 按用户：只在私聊算数

`issue_manager_user_access`、`issue_draft_user_access`、`code_reader_user_access`（以及回退用的老字段 `user_repository_access`）都按 `用户 ID = owner/repo, owner/repo` 填写。判定时取的是 `event.UserID`。

WebUI 里这一栏原来标成「私聊 / 群聊」，沿用了通知对象那套说法，把"授权对象"和"消息发到哪"混成了一个词。现在标为「按用户 / 按群」，输入框提示也从"私聊用户 ID"改成"用户 ID"。存储值没变。

但**按用户的授权只在私聊生效**。它的本意是"这个人可以操作这个仓库"，不是"这个人可以把机器人带进任何一个群往这个仓库写"——后者意味着他能在一个从没被授权聊这个仓库的群里下指令，群里所有人都看得见，上下文也能影响写进去的内容。群里能做什么，一律由群自己的配置说了算。

| 会话 | 按用户授权 |
| --- | --- |
| 私聊 | 生效 |
| 群聊 | 一律不生效，明确拒绝并说明按用户的授权只在私聊算数 |

判定收敛在 `repositoryPublishUserScopedAllowed` 一处：群聊事件直接返回 false。

## 群里的草稿谁来批

原先"群里某个人当审批人"正是靠按用户的管理员授权实现的：群内成员提草稿，某个按用户授权的人来批。把按用户的授权挡在群外会拆掉这条审批链——草稿只剩主人能批，否则就得把整个群设成管理员，那等于没有审批门槛。

所以有 **`issue_approver_group_access`「群聊草稿审批人（按群）」**，按 `群 ID = 用户 ID, 用户 ID` 填写。它仍然是群自己的配置，不是个人跨场景带权限。审批人的边界：

- 只能推动已经带确认码的草稿，**不能绕过草稿直接写**（他自己发起的写操作同样只落草稿）；
- 能批哪些仓库由**本群的草稿范围**决定，不是把整份白名单交给他；
- 写入用**他本人的 GitHub Token**，落到 GitHub 上的东西要能归因到具体的人。整个群被放开（`issue_manager_group_access`）时才用公共 Token。

## 按群：整群授权，可以再限定群身份

`issue_manager_group_access`、`issue_draft_group_access`（老字段 `group_repository_access`）按 `群 ID = owner/repo, owner/repo` 填写，授权范围是该群成员。

默认群里所有人都算数——这是老行为，不写后缀的配置读进来语义不变。要收窄就在仓库后面加身份要求：

| 写法 | 谁能用 |
| --- | --- |
| `owner/repo` | 群里所有成员 |
| `owner/repo#group_admin` | 群主和群管理员 |
| `owner/repo#group_owner` | 只有群主 |

机器人主人在哪一档都通行：主人的权限本来就不经过这份名单。

## 两个"管理"不是一回事

- **Issue 管理人员**：Diana 这个插件的授权角色，决定谁能直接写 GitHub、谁负责确认草稿。由上面那几项名单决定。
- **群主 / 群管理员 / 群成员**：聊天平台给的群内身份，由平台决定，Diana 只是读。`#group_admin` 这类后缀说的是它。

一条按群授权写成 `#group_admin`，意思是"这个群里，群主和群管理员算作 Issue 管理人员"，不是"群管理员就是 Issue 管理人员"。想在群里单独放行某个人，用「群聊草稿审批人（按群）」——按用户的授权只在私聊算数，放行不到群里。

管理人员自动也是草稿人（`repositoryPublishEffectiveAccess` 里显式合并），不必重复添加。两条授权覆盖同一个群 + 仓库时，草稿侧按更宽的那条算——否则把管理人员收窄到群管理员，会连带把本来放给全体成员的草稿权一起收走。

## 身份怎么取，取不到怎么办

先看事件自带的 `SenderRole`（OneBot 每条群消息都带 `sender.role`，Telegram 的 `creator`/`administrator`、钉钉的 isAdmin 都由 `NormalizeGroupRole` 收敛成同一套取值），拿不到再回查一次群成员信息。

查不到身份时按最严处理：除「所有成员」外一律拒绝，并在回复里说明是平台没提供群身份，而不是仓库没配。身份够不上时同样明确拒绝，提示里写清这条授权要求什么身份、当前身份是什么，以及"想在本群单独放行某个人，用「群聊草稿审批人（按群）」"。

身份查询是惰性的：一条带后缀的授权都没有时，不会为此多打任何平台接口。`github_watch` 的管理清单属于每条消息都要走的热路径，那里只认事件自带的身份，不额外回查。
