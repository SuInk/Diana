# 订阅工具：三合一

`schedule`、`rss`、`github_watch` 合并成一个 `subscription` 工具，用 `kind` 区分种类。

## 为什么合

这三样在存储层本来就是一张表：`Reminder.Kind` 取 `query` / `rss_watch` / `repository_watch`，字段摊平在同一个结构里；`tasks` 工具也早就用一个 `kind` 字段把它们一起列出来。**分裂只发生在工具层。**

代价是两个：

- 模型要先猜自己该调哪一个，猜错就白费一轮；
- 「列出来用 `tasks`、改用另外三个工具」本身就别扭——同一批数据，读写入口不一致。

合并之后 `operation=list` 不传 `kind` 就一次列出全部订阅，每条带 `kind`，这是以前要分三次调才能拿到的东西。

## 判别联合的代价，以及怎么压

合并的代价是 `kind` 选错、参数就对不上。这不是靠在描述里多写几句"请小心"能解决的，用两个结构性手段：

1. **名字不带点号，描述第一句就说"这是一个工具，不是三个"。** 这条抄 `github` 工具，那边的注释记过原因：点号命名会让弱模型把取值脑补成子工具名。
2. **`kind` 的枚举按本次会话实际可用的种类动态生成。** `kind=github` 本来就只挂给机器人主人和该仓库的管理人员——合并之后不能让所有人都在枚举里看见它。看得见模型就会去调，然后只能被拒绝，白费一轮（跨会话发送那里记过同一条教训）。没权限的人拿到的枚举里只有 `schedule` 和 `rss`；硬调 `kind=github` 会被明确拒绝并说明原因，而不是崩在 nil 上。

另外每个 kind 专属字段的说明一律以「kind=x 专用」开头：合并之后模型同时看得见三套字段，不标清楚归属就会串。

## 实现形态

`subscription` 是一个转发器，不是重写。三种订阅各自的校验、额度和权限逻辑原样保留在原来的工具里，合并只换了入口——那三套逻辑各有各的测试，不该借这次改动一起翻新。

- 转发前摘掉 `kind`：下游不认识这个字段。
- `list` 不传 `kind` 时逐个调下游的 `list` 再摊平，**不绕过它们直接查存储**：每种订阅的可见范围不同（主人能看全部、普通用户只看自己、github 还要按仓库授权过滤），绕过等于把那三套过滤重写一遍。
- 一种查失败不吞掉另外两种的结果，但会在 `message` 里说明结果不完整，不假装查全了。

## 没有一起做的

- **`run`（立刻检查一次）仍然只有 `kind=github` 有。** 对 `rss` 也说得通（"我刚发了条推，试试"），但那是新功能，不该混在合并里。对不支持的 kind 调用会明确报错并说明它支持哪些操作。
- **`rss` 的单复数重复**（`twitter_handle` / `twitter_handles`、`feed_url` / `feed_urls`，视图里还同时留着 `Sources` 和三个单数字段）是历史包袱，属于清理，和合并无关，原样带过来了。
- **一次性提醒 `reminder` 没有合进来**：它是一次性的，生命周期和这三种不同。`tasks` 也保留，它是含一次性提醒在内的总览。
