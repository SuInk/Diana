# 缓存与磁盘维护

升级备份（含升级前的数据库副本）保留最近 3 天、最多 3 份（含本次）：每次升级创建备份前，先删除超过 3 天的备份，再从最旧的开始删到只剩 2 份。新版本健康检查通过后只删除本次备份里被替换的旧程序文件，数据库备份照常保留，发现数据问题时仍可手动恢复；健康检查失败时用本次备份自动回滚。Docker 部署（拉新镜像）和源码构建没有更新器替换前的这一步：换了版本后第一次启动，会在打开数据库、执行迁移之前把它复制到 `.diana-updates/backups/<时间>-<旧版本>/database/`，计入同一套保留规则；上次运行的版本记在 `.diana-updates/last-run-version`。备份失败时不启动，数据库保持原样。安装器选择不启动时保留完整备份。一键安装器（`.installer/backups`）和控制台更新（`.diana-updates/backups`）各自计数。源码更新脚本则在构建和文件替换完成后删除临时备份（仍需手动重启，不包含启动健康检查）。若权限等原因导致删除失败，会记录警告，不能视为已释放空间。自行维护的数据备份不受影响。

磁盘维护：文件日志按 20 MiB 轮转，保留 5 份备份；数据库日志在启动后及每 24 小时分批清理，默认调试日志保留 7 天、其他日志保留 30 天。可在 `storage` 下设置 `debug_log_retention_days`、`log_retention_days`，`0` 使用默认值，`-1` 禁用对应清理。旧日志将不可再查看，但用量统计日志、聊天记录、长期记忆、配置和历史媒体不会删除。数据库空闲页供后续写入复用，已有 `.db` 文件不会立即缩小；历史媒体目录和 Docker/系统收集的标准输出日志仍需单独管理，这不是整个数据目录的容量上限。

调试模式（默认开启）记下的模型请求轨迹（事件页里的「调试轨迹」）不进数据库，存在数据库旁的 `debug-traces/` 下，按 `<UTC 日期>/<group-群号 或 private-QQ号>/<message_id>/` 分目录，每一步一个缩进排好的 JSON 文件，文件名写明序号和这一步做了什么（例如 `001-proactive_reply_router.json`、`002-reply.json`），排查时直接打开就能读。当天（UTC）的文件保持明文；之前的在每日维护时压成同名的 `.json.gz`（约为原来的三分之一），用 `gzcat` / `zless` 查看，macOS 上双击即可解压。它每轮都带着完整的模型上下文，调试模式开着时一天就有上百 MB，放进库里只会让 `.db` 越来越大。按 `debug_log_retention_days` 整天删除目录（所以最多比设置多留一天），跨群检索记录等其余调试日志仍在数据库里按原规则清理。内存数据库没有旁边的目录，轨迹照旧写进库里。升级前已经写进库的轨迹照常能看，到期后随调试日志一起清掉。

长期记忆的提取任务处理完后保留 7 天（入队时靠它识别重复投递的同一条消息），之后删除；待处理和处理中的任务不受影响。

两类数据移出或删掉之后，库里腾出的是空闲页，`.db` 文件本身不会缩小。要把文件真正缩下来，需要停掉服务后对数据库执行一次 `VACUUM`（期间需要和数据库文件差不多大的空闲磁盘）。

媒体去重：新写入的历史媒体（含 Telegram 文件、音视频和图片）在各自存储目录内按文件内容 SHA-256 共用一份文件，不再按消息重复落盘；普通图片缓存的远程下载和生图结果也共用内容文件。相同图片 URL 通过持久化来源索引复用；Telegram 优先按同一 API 服务的 `file_unique_id` 在下载前复用，缺失时按同一 Bot 的 `file_id` 复用，贴纸缩略图使用自己的标识。OneBot 图片、视频及文件解析支持的附件支持明确的 `md5`、`file_md5`、`fileMd5` 字段，首次下载核对成功后可跨 URL 复用，不从文件名或不透明文件 ID 猜测 hash。相同来源或稳定标识的并发请求只下载一次；索引最多保留 4096 项，内容丢失或 SHA-256 校验失败时重新下载。不同新地址没有已知稳定标识时，首次仍需下载后判断；MD5 与内容不符时保留可用媒体，但不记录该 MD5 映射。旧路径继续可读，不自动迁移或删除历史重复文件；独立的历史媒体与容量受限的图片缓存不合并，以免缓存淘汰破坏聊天历史。

视频与附件下载缓存位于历史媒体目录的 `download-cache` 子目录，流式下载后按 SHA-256 存储。默认按最后使用时间保留 7 天，不限制总容量。可在 **设置 → 系统 → 下载缓存** 中选择按闲置天数清理、仅按容量清理或永不自动清理；按天数模式可同时启用容量上限。**WebUI 保存后立即生效，无需重启**，已在读取的文件仍受到保护；设置持久化到数据库，重启后优先于 YAML。尚未通过 WebUI 保存时，使用 `config.yaml` 的 `storage.download_cache_retention_days`（0 默认 7 天，-1 关闭按天数清理）及 `download_cache_max_mb`（MiB，0 不限容量）作为启动回退值。YAML 的永不清理组合为 `-1` 和 `0`。启动时、每 24 小时、保存设置及最后一个下载或解析任务释放文件时检查清理。清理不删除历史截图，也不删除 QQ 原始目录中的文件；除永不清理模式外，异常退出遗留的未完成下载在超过 7 天后清理。来源索引仍最多保留 4096 项，仅删除索引元数据、不删除对应文件。缓存命中仍检查文件完整性及当前解析大小限制；淘汰后再次使用会重新下载。公开视频下载与适配器附件的来源索引隔离，保持现有网络访问限制；正文中的普通文件链接仍按原流程读取，不作为固定附件缓存。

历史媒体原件（`history-media` 中除 `download-cache` 外的图片、视频、音频、PDF 和文件）使用独立策略。升级后默认不自动删除；管理员可在 **设置 → 系统 → 历史媒体原件** 设置保留天数和容量上限。保存后立即清理，之后在启动及每 24 小时检查。超期文件先删除，超过容量时再从最旧原件开始淘汰；聊天文字、媒体类型和已生成摘要仍保留，读取已删除原件时按“不可用”处理。`-1` 表示不按时间删除，`0 MiB` 表示不限制容量，两者组合即永不自动清理。下载缓存、来源索引和正在写入的临时文件不计入该容量，也不会被这套策略删除。

## 存储空间总览

**设置 → 系统 → 存储空间** 回答两件事：数据目录所在的那块盘还剩多少，以及数据目录被哪类文件占掉了。上面的饼图以整块盘为分母，分成 Diana 数据目录、其它程序与系统、可用空间三段；磁盘容量取数据目录所在挂载点，容器里看到的是挂载卷的容量，不是宿主机整机。读不到容量时（例如权限受限）饼图退回只画数据目录，并在卡片上说明原因。

下面那条以数据目录自身为分母，按扩展名分成数据库、图片、视频、音频、文档与压缩包、其它文件——一台几百 GB 的机器上 Diana 常常连 1% 都不到，两处用同一个分母会让分类细得看不见。分类只看扩展名，没有扩展名的文件（例如下载缓存里尚未定型的内容文件）计入「其它文件」。

第三块「按目录」以数据目录的顶层目录拆开（历史媒体原件、下载缓存、手动备份、内置浏览器……），Agent 工作目录再细分到长期保存、下载、产出、临时文件、回收站、编码工作区等分区，看得出几个 G 的图片到底堆在哪里。

遍历数据目录不便宜（媒体缓存可能有几十万个文件），所以接口永远返回上一次的遍历结果，超过一分钟后在后台重算：首次打开会显示「正在重新统计」，页面每两秒自动重试，直到拿到结果。这里只统计、不删除；要清理见上面的下载缓存与历史媒体原件两节。

## Agent 工作目录

工作目录（数据库旁的 `workspace/`）按分区每天清理一次，启动时先跑一轮：`tmp/` 超过 1 天、`downloads/` 和 `.agent-browser/` 超过 7 天、`outputs/` 超过 30 天的文件删除，按文件修改时间算；`.trash/` 按删除时间，7 天后永久清理。长期保存区 `keep/`、运行时状态 `.diana/`、Skills（`.agents/`、`skills/`）、编码代理的 `coding/`、`coding-runtime/` 以及凭据文件永远不碰。工作目录根下散落的文件、没有机器人配置引用且 30 天没动过的 `coding/<仓库>` 只报告不删除：写进应用日志（动作 `workspace_cleanup`，只在确实删了东西的那天记一条），也列在 **设置 → 系统 → 工作目录** 里。

同一轮还会清掉系统临时目录里 Diana 自己留下、超过 1 天的 `diana-*` 目录和文件（转码、生图、渲染、语音识别的临时目录，进程被杀时会遗留）。按修改时间判断，不区分是哪个进程建的：同一台机器上几份 Diana 共用临时目录，一天足够把正在处理的任务排除在外。

历史媒体原件的默认策略不变（默认永不自动删除），这里只在存储页里单独显示它的占用。

## 跨机器人来源复用

同一 Diana 进程内，RSS 的原始 Feed 结果缓存 30 秒，按规范化来源地址与抓取配置复用，并合并兼容的并发请求；各订阅仍分别按自己的游标和条目上限选择新内容。新建订阅始终读取新鲜基线，并使旧缓存及尚在运行的旧缓存写入失效，避免游标倒退。查询参数保留在来源键中，私有 Feed 的不同访问参数不会共用结果。

链接解析共享未进行平台投递排版的解析结果：只有 URL、有效凭据、Cookie 文件内容及解析参数一致才复用，不按机器人 ID 阻止相同工作。QQ 和 Telegram 的格式化、发送与失败重试仍各自执行。Cookie 文件改变或缓存媒体文件被清理后会重新解析；可变的浏览器登录态、Cookie jar 和网页浏览器渲染路径不共享结果。解析缓存时长仍跟随各机器人配置，关闭解析缓存也关闭相应并发复用。

RSS 判断结果最多缓存 10 分钟，仅在完整素材、判断规则、来源设置和模型配置一致时复用，模型配置包含提供商凭据、参数与降级路由；模型配置变化会使原结果不再命中。无法核验模型身份的自定义工厂及含动态 OAuth 凭据的配置跳过判断复用。通知游标、发送状态和订阅 ID 不共享，A 发过或发送失败都不代表 B 已经收到。

共享缓存只存在于内存，重启后重新建立。每类最多 64 项、16 MiB，单项超过 4 MiB 不保存。失败和无效结果不保存；取消一个等待请求不会取消其他等待者，共享操作仍受独立超时约束。本机制不自动合并、删除或修改任何订阅配置。

## 控制台记录

事件页停留时不自动替换列表，只提示“有新事件”；点击提示或刷新按钮后重新读取。离开页面停止刷新，返回时重新加载，迟到的旧请求不会覆盖当前列表。

人员页的结构化长期记忆列表和计数按机器人及账号精确读取，空机器人 ID 只对应旧版无命名空间记录。可编辑的“最近发言”是排查缓冲，不是结构化长期记忆；删除人员档案保留结构化长期记忆和聊天记录。
