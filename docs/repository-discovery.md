# 推荐 GitHub 仓库时的影响力指标

`github` 工具原来只做 Issue 与 Pull Request。用户问「有没有好用的 X 库」时，模型手里没有任何仓库级事实，只能靠网页搜索的标题和简介来推荐——而简介不会告诉你这个仓库有多少人在用，也不会告诉你它最后一次提交是 2022 年。

现在同一个工具多了两个只读操作：

- `repo_search`：按关键词找公开仓库，用于「推荐一个」。
- `repo`：读单个仓库，用于用户已经点名某个仓库时核对。

两者返回同一份画像，重点是三项：

| 字段 | 含义 | 用来判断 |
| --- | --- | --- |
| `stars` | star 数 | 多少人在用，是否已被验证过 |
| `forks` | fork 数 | 多少人真拿去改、提 PR，不只是收藏 |
| `pushed_ago` | 最近一次推送距今多久 | 还有没有人维护 |

外加两个标记：`stale`（超过一年没有推送）和 `archived`（仓库已归档）。工具描述要求模型把这三项写进给用户的回复，并在 `stale` 或 `archived` 为真时明说，不能当作可用推荐照样给出去。`fork` 为真说明这个仓库本身是别人的分叉，推荐前先看上游。

## 几处刻意的取舍

- **新鲜度取 `pushed_at`，不取 `updated_at`。** 后者改个简介、加个 topic 就会往前跳，用它判断维护状态会把早就停更的仓库说成刚更新过。只有 `pushed_at` 缺失时才回落到 `updated_at`。
- **不返回 `watchers_count`。** GitHub 在这个字段上回填的是 star 数而不是订阅人数，一起返回只会让模型以为拿到了第三个独立指标。真正的订阅数是 `subscribers_count`，而仓库搜索接口不提供，两个操作的字段无法对齐。
- **`repo_search` 只搜公开仓库。** 它走的是公共凭据，带 Token 时 GitHub 会把这个 Token 看得见的私有仓库一并搜出来。查询里固定拼上 `is:public`，返回结果再按 `private` 过一遍，两道都不省。
- **限定符由后端拼。** `query` 只收普通关键词，`language:`、`sort:` 这类限定符和布尔操作一律拒绝，和 Issue 搜索同一套校验；按语言筛选走 `language` 参数，换排序走 `sort`。校验不碰网络，注入类输入零请求被拒。
- **`repo` 按仓库可见性分流。** 它和 `get`、`pull_files`、`commit_files`、`compare_files`、`read_file`、`list_files` 走同一套读 ACL：公开仓库全员可读，私有仓库仅主人和「私有仓库源码读取授权」名单内的用户可读，不能靠「只看 star 数」绕过授权。
- **两者都不进操作审计。** 纯查询不写 GitHub，也不把这一轮回复标成有外部副作用。
