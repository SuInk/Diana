# 小窝视频复核与高星项目实现调研

调研日期：2026-11-02。本文是实现方向建议，不表示相关能力已经进入 Diana。

## 结论

当前小窝实现是「近期消息事件 → 姿势」的展示层。视频呈现的是「用户意图 → 活动切换 → 房间里的连续动作 → 外部操作及回复 → 活动结束」；二者不是同一层次。下一版重点应是明确的活动协议和行为状态机，而不只是把 SVG 换成 Live2D。

## 视频复核

群消息仍为 `1127671893 / 996661569`。原下载 URL 返回 HTTP 400，但通过代码中的 URL 来源索引算法，在 miku 下载缓存中找到与该 URL 对应的原文件：约 9.49 MB，1280 × 720，时长 121.323 秒，包含音轨。

本次按每两秒一帧检查了覆盖全片的画面和可见字幕，不是只看之前的 8 张抽帧；没有做音轨听辨，也没有取得视频作者的源代码或后台日志。以下时间为近似分段。

| 时间 | 可观察到的内容 |
| --- | --- |
| 0–20 秒 | 展示聊天窗口，字幕说明给角色接入房间；发消息后，角色在床上拿手机，并出现回复 |
| 20–42 秒 | 用户发送打开电脑刷抖音的请求，画面切回角色在床上看手机 |
| 42–60 秒 | 角色放下手机、坐起，台灯亮起，角色离开床边来到椅子和电脑前 |
| 60–86 秒 | 角色面对亮屏电脑；另一个真实桌面窗口显示抖音页面，播放内容发生变化；字幕称这是角色自己的账号 |
| 86–104 秒 | 聊天窗口出现观看内容的反馈，随后用户要求回床上休息、不玩了 |
| 104–121 秒 | 字幕称抖音停了；角色离开电脑并回到床上，聊天窗口出现回应 |

可确认的是视频演示了这一套联动效果。不能仅凭录像确认：使用哪个开源项目、是否采用 Live2D、是否为预录动画片段、动作由模型还是规则选择、外部页面由什么工具操作、是否全程自动，以及是否存在剪辑。不会把作者的字幕说明当成已验证的后端执行证据。

相比当前实现，最值得保留的是：**活动有开始和结束，物品位置和场景状态连贯，角色动作与聊天意图有关，而不是任何消息都去书桌前。**

### Star-Office-UI：显式报状态，而不是猜聊天内容

- 后端支持 `idle / writing / researching / executing / syncing / error`，状态保存在服务端文件中。
- `/set_state` 接收状态和说明；项目 Skill 提示 Agent 在开始任务前设置工作状态，结束后设置 idle。这是一种协作约定，不等于它能自动观察任意 Agent 的完整执行链。
- 前端读取 `/status`，通过状态到区域的映射切换视觉，`moveStar` 负责移动和途中摆动。
- 服务端存在超时回 idle 的兜底。当前 `load_state` 实际默认值是 300 秒，邻近注释仍写 25 秒，应以执行代码为准。
- 值得借鉴：显式状态、服务端一致性、过期兜底。Diana 已有事件总线，不需要额外运行它的 Flask 服务，也不需要照搬前端轮询。

代码依据：[状态接口](https://github.com/ringhyacinth/Star-Office-UI/blob/f29c107e9728a72f2635f10b4e8203b29b37221d/backend/app.py#L1290)、[状态读取和移动](https://github.com/ringhyacinth/Star-Office-UI/blob/f29c107e9728a72f2635f10b4e8203b29b37221d/frontend/index.html#L4665)。

### AIRI：模型选择有定义的动作，播放器执行

- `formatLive2DActPrompt` 把当前模型可用且启用的表情和动作标识写入提示，要求只用清单里的精确名称。
- 模型可输出 `<|ACT {"expression":{"name":"…","duration":3}}|>`、`<|ACT {"motion":"…"}|>` 等控制标记。
- `Stage.vue` 订阅控制信号，解析并规范化 ACT 载荷，再调用 `live2d.motions.execute` 或 `live2d.expressions.execute`；情绪也可映射到不同渲染器的表现。
- 语音口型另由音频驱动模块处理，不要求语言模型逐帧输出嘴形。
- 值得借鉴：动作能力清单、控制数据与对话文本分离、动作执行层与渲染技术分离。不能由这些模块直接推出它提供了视频里的完整卧室活动系统。

代码依据：[可用动作提示](https://github.com/moeru-ai/airi/blob/cc278a3210a7fc02ad061ded9564a8810c583dad/packages/stage-ui/src/constants/prompts/live2d-act.ts)、[控制信号消费](https://github.com/moeru-ai/airi/blob/cc278a3210a7fc02ad061ded9564a8810c583dad/packages/stage-ui/src/components/scenes/Stage.vue#L317)、[音频口型驱动](https://github.com/moeru-ai/airi/blob/cc278a3210a7fc02ad061ded9564a8810c583dad/packages/model-driver-lipsync/src/live2d/index.ts)。

### Open-LLM-VTuber：表情随回复片段一起传输

- 从模型输出中提取 `[情绪名]` 标签，通过角色自己的 `emotionMap` 转为表情索引。
- `actions_extractor` 把表情附着到句子输出，后续与显示文本、TTS 文本一起进入语音处理。
- 发给前端的音频载荷同时携带 `audio / volumes / slice_length / display_text / actions`，不是前端看到一句消息后自己猜表情。
- 值得借鉴：动作、文本、语音的关联与分段。它解决的是说话时的角色表现，不自动解决走到床边或操作真实电脑。

代码依据：[动作提取](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/992309c0aa19845960228f880013d4685fde93b5/src/open_llm_vtuber/agent/transformers.py#L58)、[音频与动作载荷](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/992309c0aa19845960228f880013d4685fde93b5/src/open_llm_vtuber/utils/stream_audio.py#L50)。

## Diana 推荐的分层

```text
运行时任务事件 ────→ 真实任务状态（按机器人、任务 ID 隔离）
模型选择的房间动作 → 白名单校验 → 活动状态与动作队列
                                      ↓
                              SSE 快照和增量事件
                                      ↓
                         房间状态机 → SVG / Live2D 渲染器

浏览器、桌面等真实工具 → 原有授权与执行 → 执行结果反馈
```

1. **真实执行状态由运行时产生。** 开始、工具执行、成功、失败和取消不依赖模型记得报状态，也不再用「最近 90 秒有消息」替代。
2. **角色自主活动由模型选择。** 单独提供受限的 `room` 工具（建议名），只允许从当前素材支持的动作中选，例如休息、看手机、去书桌；不要开放任意脚本、URL、文件路径或支付能力。
3. **复杂动作由状态机展开。** 模型只需表达「去书桌」，前端或活动调度层负责放下手机、起身、移动、坐下、亮屏，避免要求模型逐帧指挥。完成、失败和取消应有明确协议。
4. **房间行为不等于真实操作。** 坐到电脑前可以只是叙事；确需打开应用时必须走现有浏览器/桌面工具及授权，工具成功后才能显示或回复操作成功。
5. **持久活动与短期执行分开。** 房间位置、道具状态可保存；运行中的任务应有 task ID、序号、截止时间和终态，重连后用快照恢复，旧事件不能复活已结束任务。
6. **模型指令是可选表现，不应阻塞核心回复。** 缺失模型、缺失动作、播放失败时回退静态表现；离线时不能让虚构动画驱动真实任务。

建议顺序：先把后端真实活动事件与受限房间工具接好，再升级 Live2D/素材和连续过渡。当前 SVG 可作为协议调试用渲染器和加载失败的回退，而非最终美术方案。
