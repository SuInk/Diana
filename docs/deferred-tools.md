# 延迟工具调用协议

配置 `CoreTools` 后，MCP 与内置的非 core 工具统一通过固定的 `tools_load` / `tools_execute` 协议调用。未配置时维持全部工具直接声明的兼容模式。

1. 从系统提示词目录选择工具，调用 `tools_load({"names":["目标工具名"]})`。
2. 读取结果 `loaded` 中的完整 `description` 和 `inputSchema`。
3. 调用 `tools_execute({"name":"目标工具名","input":{...}})`；兼容 JSON action 协议也使用此信封。

## 常驻档位

默认常驻名单写在代码里（`replyAgentCoreTools`），按线上运行占比排。用户可以在扩展页的「上下文」标签里逐项改：每个内置工具一档，每条 MCP 服务一档（管它的全部工具），Skill 的档位在 Skills 标签里。三档是**跟随默认 / 常驻 / 按需**——档位表里没有这个键就是跟随默认，所以「默认」和「按需」在文件里不是一回事。

档位按机器人存在 `.extension-overrides.json`，和启用开关、成员权限同一份文件，键名加 `resident:` 前缀（`resident:tool:poke`、`resident:mcp:gitea`、`resident:skill:foo`）。运行时在注册表建好之后才算常驻名单：档位是按扩展配的，得知道这一轮实际注册了哪些工具、哪条服务带了哪几个。

「上下文」标签显示的是**最近一轮真实用过的工具目录**。内置工具是按平台、权限和插件开关逐轮拼出来的，没跑过一轮就无从知道这台机器人到底有哪些，所以冷启动时这一页是空的。

改档位会改请求里的 `tools` 数组，等于把所有会话的前缀缓存清一次；常驻项每轮都要掏 token，按需的只在用到那一轮多一次 `tools_load` 往返。

## Skills 目录

Skill 走同一套「目录在外、正文按需」的思路，但目录不进系统提示词：它按机器人、按群分档开放，装一个卸一个也会变，放进系统提示词等于每换一个群就把整条 prompt 的前缀缓存作废。

系统提示词里只留一条规则，指向目录并要求先 `read_skill`。目录本身（每条只有名称和用途，不含磁盘路径，受 `SkillsListBudget` 限制）随请求挂在消息末尾的易变块里，排在调用方的人设、历史和缓存断点之后，当前轮仍是最后一条。会话里没有可用 skill 时这一段整段不出现。

这一段用 **user role**：它是「本轮随消息带来的资料」，不是恒定的系统约束，和它挨着的当前消息同属一轮；命中触发词时它每轮内容都不一样，更该待在缓存断点之后。

正文仍然只能由 `read_skill` 取回，返回值里带 `path`，`SKILL.md` 中的相对路径按它所在目录解析。

正文随请求下发的有两种情况，这时模型不必再 `read_skill`：

- **配成常驻**的 Skill，每轮都带。
- **声明了触发词**的 Skill（`SKILL.md` frontmatter 里的 `keywords`，写成列表或逗号分隔都行），在最近几条用户消息里命中时才带；用户用 `$SkillName` 点名时同样带。回看多少条由 `SkillTriggerScanDepth` 控制，默认 2 条。匹配是大小写不敏感的子串，不按整词——中文不用空格分词，整词匹配对它是错的。

档位优先于触发词：配成常驻就永远带，配成按需就永远不带（声明过触发词也不自动带）。没配过档位才看触发词。

这一档解决的是另一个问题：上下文一长，模型按目录去 `read_skill` 这一步经常不做，写得再细的 Skill 也等于没有。把判定放回运行时就不存在漏读，也不多花一次往返。正文在一次请求里有总量上限（`ResidentSkillBodyBudget`），超出的那几个退回目录行。

目录、Skill 和历史记录里的工具名称不授予直接调用权限。加载状态只在当前 `Runner.Run` 有效，每条新用户消息开始后必须重新加载。Core 工具仍可直接调用。

`tools_load` 每次接受 1–8 个名称；完整 JSON 结果最多 131072 个 Unicode 字符。整个批次成功且结果未超限才登记加载状态，不截断描述或 schema；未知名称、已移除工具或超限会明确报错。契约使用独立上限，不受普通工具输出截断设置影响。

执行前检查当前 registry view 中工具仍存在，并按加载时和执行时的 schema 分别校验。使用 JSON Schema 校验器支持 required、类型、枚举、嵌套结构、组合约束和本地引用等；不自动转换参数类型。外部 `$ref` 不联网解析，无法解析的契约拒绝执行。校验错误返回字段路径与约束位置，不回显参数值。

直接调用延迟工具、未加载执行、工具消失、信封或参数无效均进入有次数上限的协议修复，记录为 skipped，不消耗真实工具执行预算，不访问 MCP 上游。

`tools_load` 和只读自省工具不占 `MaxSteps`，各自有独立配额（4 次和 6 次）。「为了把活干对先问一句」不该和干活抢预算——扣预算等于逼模型少问、凭记忆猜。

是不是自省由工具自己声明（实现 `agent.IntrospectionTool`），runner 不维护名单：它认不得以后才加的工具，写死一张名单只会漏。门槛是三条同时成立，不是「跑得快」——**只读**（不改状态、不对外产生动作）、**本地**（不看别人服务的脸色）、**自省**（答案是 Diana 自身的能力、身份、配置，而不是任务本身的进展）。快但会写的工具（改配置、发消息、戳一戳）照常占预算：步数预算约束的是干活，不是延迟。

同一个工具可以一半只读一半是动作，所以声明方法收的是入参：目前 `capabilities`、`list_capabilities`、`identity_check`、`read_skill` 整体声明，`extension_access` 只在 `action=list` 时声明。

「查无此工具」和「没有权限」分开报错：名称在当前注册表里不存在时提示重新选择；名称是被身份白名单摘掉、被机器人开关停用，或只存在于共享底座却不在本次会话权限内时，明确说明这是权限问题且重试无效，模型应改为说明需要主人操作。主人会话没有白名单，拿不到的名字一律按不存在处理。

Runner 在执行管线入口展开信封：权限确认、最小参数过滤、重复调用检测、工具预算、超时、搜索证据账本、终止结果和图片附件继续使用真实工具名。Provider 历史保留原始 `tools_execute`、call ID 和供应商续接数据；并行调用仍每步只执行一个，其余返回未执行结果。身份隐私代理递归处理 `input` 中的标识，回放前重新脱敏。

同一能力集合内，加载前后 API 工具名称、顺序和 schema 保持稳定。搜索主张 ID、来源 URL 和图片 pending 状态不再改变原生声明；搜索/收尾使用固定 superset schema，动态条件通过工具结果和 Runner 本地检查执行。预算耗尽的最终收尾请求仍仅提供 `agent_finalize`，这是明确的阶段切换。

运行日志和跨轮记忆记录实际目标工具，`tools_load` / `tools_execute` 自身不进入最近调用记忆；仅加载和校验失败不会被记录成目标执行成功。现有 Tool 实现和 MCP server 无需修改。
