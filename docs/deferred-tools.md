# 延迟工具调用协议

配置 `CoreTools` 后，MCP 与内置的非 core 工具统一通过固定的 `tools_load` / `tools_execute` 协议调用。未配置时维持全部工具直接声明的兼容模式。

1. 从系统提示词目录选择工具，调用 `tools_load({"names":["目标工具名"]})`。
2. 读取结果 `loaded` 中的完整 `description` 和 `inputSchema`。
3. 调用 `tools_execute({"name":"目标工具名","input":{...}})`；兼容 JSON action 协议也使用此信封。

## 常驻工具名单与前缀缓存

每轮都带完整定义的那几个工具，是一份**名单**，不是一组开关。界面（机器人配置 →「上下文」）只有两个动作：把东西**加进名单**，或者**从名单里拿走**。

名单的成员可以是三种 ID：一个插件（`official.music`，它供给的工具全带上）、一条 MCP 服务（`mcp:gitea`，同理）、一个工具（`tool:web_search`）。整条加进来还想少带其中一个，就改成把其余几个逐个加进名单——不需要「排除」这种反向状态，名单里写的就是最终结果。

没列过名单的机器人跟着内置推荐名单走（`replyAgentCoreTools`，按线上运行占比排）。一旦列了自己的名单，就完全以名单为准：**以后版本往推荐名单里加的新工具不会自动进来**，界面上「恢复推荐名单」把这台机器人的名单整个撤掉，重新跟着版本走。这是「只有加和删」必然的代价，换来的是所见即所得——屏幕上那一份就是请求里那一份。

空名单和没列过名单不是一回事：前者是「一个工具都不常驻」，后者是「跟着推荐走」。文件里用 `residency:list` 这个键区分。

名单按机器人存在工作目录的 `.diana/extension-overrides.json`，和启用开关、成员权限同一份文件，成员键加 `resident:` 前缀（`resident:tool:poke`、`resident:mcp:gitea`、`resident:official.music`）。界面保存时整份写：名单本来就是一整件事，分几次写中间会出现「插件进去了、单独拿掉的那个还没拿掉」这种谁都不想要的状态，而它每变一次，所有会话的工具列表就跟着变一次。

**Skill 不在这份名单里。** 所有 Skill 只列名称和用途，正文按需通过 `read_skill` 读取。界面不再提供 Skill 正文的常驻或触发词注入档位；旧的 Skill 常驻设置不再生效，关键词仅保留为扩展发现信息。

档位列表显示的是**最近一轮真实用过的工具目录**。内置工具是按平台、权限和插件开关逐轮拼出来的，没跑过一轮就无从知道这台机器人到底有哪些，所以冷启动时这一页列不出细节。但名单里的项仍然会露面（标成「目录未加载」）：名单写在文件里，重启后照样生效，这时候显示成「没配过」会让人以为配置丢了。

改名单会改请求里的 `tools` 数组，可能让下一轮请求无法复用原来的前缀缓存；名单里的每轮都要掏 token，名单外的只在用到那一轮多一次 `tools_load` 往返。这个代价界面上是具体数字，不是一句提醒：每一项都按**实际发出去的那份**估算两边开销——名单里是整份工具定义（`ToolDefinitionFor` + `llm.EstimateToolDefinitionTokens`），名单外是目录里的那一行——页顶给出当前合计，增删当场结算成增减。

也因为这个代价，名单是**跟着这一页的保存按钮一起写**：下一轮对话读到最终状态，不为每个尚未保存的调整改变工具定义。

## Skills 目录

Skill 走「短目录＋按需读正文」的方式。目录按机器人、群权限和已安装扩展生成，放在历史后的本轮资料里，不插入稳定历史之前。

目录本身（每条只有名称和用途，不含磁盘路径，受 `SkillsListBudget` 限制）随请求挂在消息末尾的易变块里，排在调用方的人设、历史和缓存断点之后，当前消息仍是最后一条。会话里没有可用 Skill 时这一段整段不出现；目录未列完时可查询 `list_capabilities`。

这一段用 **user role**：它是本轮能力发现资料，不是用户发言，也不包含 Skill 正文。

读取正文的主入口是 `read_skill`，返回值里带 `path`，`SKILL.md` 中的相对路径按它所在目录解析。用户用 `$SkillName` 点名、消息命中 frontmatter 的 `keywords` 或旧配置把 Skill 标成常驻，都不会自动展开正文。运行时仍兼容显式调用 `tools_load` 并传 Skill 名读取正文；这也是一次按需工具调用，不会在后续轮次自动回贴正文。

短 Skill 默认一次返回全文。长文按现有工具输出额度返回完整 JSON 页，`offset` / `limit` 按 Unicode 字符计数；出现 `has_more: true` 时用返回的 `next_offset` 继续调用 `read_skill`，直到 `has_more: false`。`tools_load` 的兼容入口仍要求单次返回全文，超过它原有的整批契约额度会明确报错并引导改用 `read_skill` 分页。

## 加载状态只属于本次运行

目录、Skill 和历史记录里的工具名称不授予直接调用权限。群聊、私聊和管理会话的加载状态都只在当前 `Runner.Run` 有效：本次运行已加载的工具可继续使用，新的运行按需重新 `tools_load`。不再保存跨轮已发现工具，也不恢复或自动回贴之前加载过的完整契约。Core 工具仍可直接调用，持久群历史仍由[群提示词缓存](group-prompt-cache.md)维护。

`tools_load` 每次接受 1–8 个名称；完整 JSON 结果最多 131072 个 Unicode 字符。整个批次成功且结果未超限才登记加载状态，不截断描述或 schema；未知名称、已移除工具或超限会明确报错。契约使用独立上限，不受普通工具输出截断设置影响。

执行前检查当前 registry view 中工具仍存在，并按加载时和执行时的 schema 分别校验。使用 JSON Schema 校验器支持 required、类型、枚举、嵌套结构、组合约束和本地引用等；不自动转换参数类型。外部 `$ref` 不联网解析，无法解析的契约拒绝执行。校验错误返回字段路径与约束位置，不回显参数值。

未加载却直接按名称调用已登记的延迟工具时，只返回已加载的契约和「本次未执行」，下一步再调用；本次运行已加载的直接调用仍经过同一套校验。未加载执行、工具消失、信封或参数无效进入有次数上限的协议修复，记录为 skipped，不消耗真实工具执行预算，不访问 MCP 上游。

`tools_load` 和只读自省工具不占 `MaxSteps`，各自有独立配额（4 次和 6 次）。「为了把活干对先问一句」不该和干活抢预算——扣预算等于逼模型少问、凭记忆猜。

是不是自省由工具自己声明（实现 `agent.IntrospectionTool`），runner 不维护名单：它认不得以后才加的工具，写死一张名单只会漏。门槛是三条同时成立，不是「跑得快」——**只读**（不改状态、不对外产生动作）、**本地**（不看别人服务的脸色）、**自省**（答案是 Diana 自身的能力、身份、配置，而不是任务本身的进展）。快但会写的工具（改配置、发消息、戳一戳）照常占预算：步数预算约束的是干活，不是延迟。

同一个工具可以一半只读一半是动作，所以声明方法收的是入参：目前 `capabilities`、`list_capabilities`、`identity_check`、`read_skill` 整体声明，`extension_access` 只在 `action=list` 时声明。

「查无此工具」和「没有权限」分开报错：名称在当前注册表里不存在时提示重新选择；名称是被身份白名单摘掉、被机器人开关停用，或只存在于共享底座却不在本次会话权限内时，明确说明这是权限问题且重试无效，模型应改为说明需要主人操作。主人会话没有白名单，拿不到的名字一律按不存在处理。

Runner 在执行管线入口展开信封：权限确认、最小参数过滤、重复调用检测、工具预算、超时、来源回溯、终止结果和图片附件继续使用真实工具名。Provider 历史保留原始 `tools_execute`、call ID 和供应商续接数据；互不依赖的只读 `web_search` / `browser_render` 可并行，其他调用仍按执行顺序处理，未执行的调用返回明确结果。身份隐私代理递归处理 `input` 中的标识，回放前重新脱敏。

同一能力集合内，加载前后 API 工具名称、顺序和 schema 保持稳定。搜索主张 ID、来源 URL 和图片 pending 状态不再改变原生声明；搜索/收尾使用固定 superset schema，动态条件通过工具结果和 Runner 本地检查执行。预算耗尽的最终收尾请求仍仅提供 `agent_finalize`，这是明确的阶段切换。

运行日志和跨轮记忆记录实际目标工具，`tools_load` / `tools_execute` 自身不进入最近调用记忆；仅加载和校验失败不会被记录成目标执行成功。现有 Tool 实现和 MCP server 无需修改。

最近搜索候选 URL 不再逐轮自动注入。模型可用 `chat_history` 查已发送的正文链接，但该工具不返回历史 `browser_render` 的调用参数。管理员可通过已保存的调试追踪核对原调用；模型未保留的来源需要重新检索，不保证完整恢复上一次搜索的全部候选。
