# 零花钱钱包（设计稿）

> 状态：设计中，尚未实现。本文先确认方向，定稿后再拆实现 PR。

钱包让机器人有一笔自己的零花钱：主人发零花钱，她会攒钱、记账、有想买的东西，想买时向主人提出，主人点头才算买下。第一阶段**全部是虚拟账本，不接任何真实支付**；结构按「授权书」思路设计，以后要接真实扣款时只替换执行那一步。

## 为什么不接真钱

调研结论（2026-10）：

- QQ 侧没有路。SnowLuma 不解析红包（[SnowLuma#279](https://github.com/SnowLuma/SnowLuma/issues/279)「群红包消息只能解析到降级文本」以 Not planned 关闭），也没有钱包或余额接口；NapCatQQ 只在类型里留了 QQNT 内核的 `grabRedBag` 等方法签名，没有暴露成 OneBot 动作。自动领红包、自动付款也是封号高发区。
- 通用 Agent 支付协议还早：x402、coinbase/agentkit 走稳定币；Google AP2、OpenAI/Stripe ACP、Stripe 限额虚拟卡都依赖海外商家和支付体系，国内接不上。
- 群里任何人都能和她说话。只要模型手里有能直接付款的工具，一句话术或网页里的一段注入就可能把钱转走，而且不可撤销。

所以第一阶段的目标是「像真人一样有物欲、会花钱」的体验，而不是让 Agent 真的能付款。

## 和现有机制的分工

- **SOUL.md** 定性格（省钱还是爱买），钱包不改它。
- **好感度** 不和钱挂钩：不能花钱买好感，打赏也不加分。好感度一律不决定能力，这条原则不变（见 `relationship.go`）。
- **自述** 是她对自己的描述；钱包是事实账本。两者都是机器人级、跨群生效，存储和注入方式沿用自述的做法。
- **长期记忆**：每笔买下的东西写一条事件记忆，让她之后能自然地提起「上周买的那本画集」。

## 核心概念

### 授权书

主人在 WebUI 里设一份授权书，对应 AP2 里的 Intent Mandate，只有主人能改：

| 字段 | 含义 | 缺省 |
|---|---|---|
| `allowance` | 每期零花钱 | 0（不自动发） |
| `allowance_period` | 发放周期：每周或每月 | 每月 |
| `single_cap` | 单笔上限，超过直接拒，不进审批 | 0（不限） |
| `auto_approve_below` | 低于此额自动批准 | 0（全部要审批） |
| `period_cap` | 每期花费上限 | 0（不限） |
| `currency_label` | 显示单位 | 「元」 |

金额一律以「分」存整数，避免浮点误差。

### 账本

只追加，不修改。每行一笔：

- `kind`：`allowance`（零花钱）、`tip`（打赏）、`spend`（花费）、`refund`（退回）、`adjust`（主人调账）
- `amount`（带符号）、`balance_after`、`reason`
- 来源：会话、群、消息号、触发人；关联的 `proposal_id`

余额以最新一行的 `balance_after` 为准。写入和余额检查在同一个事务里，两个群同时花钱不会透支。

### 愿望单

她自己记下想要的东西：名称、估价、为什么想要、可选链接，状态有 `wanted`、`proposed`、`bought`、`dropped`。在册上限 20 条，写满时和自述一样报容量错误，让她自己删，不静默淘汰。

### 购买提议

对应 AP2 里的 Cart Mandate。她决定买某样东西时生成一份提议（物品、价格、理由），流程是：

1. 先检查单笔上限、每期上限和余额，不满足直接告诉她原因（「钱不够」本身就是好素材）。
2. 低于 `auto_approve_below` 时直接成交。
3. 否则私聊主人，附带确认码。确认码复用编码任务审批的做法（`coding_agent_approval.go`）：码由提议内容哈希得出，只认主人本人消息里出现的码，别人说「同意」或网页正文里写着「同意」都放行不了。
4. 主人回同意码就成交并扣款；回拒绝码或超时（默认 24 小时）就作废，余额不动。
5. 成交后写账本、把愿望单条目标成 `bought`、写一条事件记忆，再回到原会话告诉大家结果。

第二阶段接真实支付时，只在第 4 步「成交」之后加一个执行器（主人手动付款回填单号，或调用限额卡接口）。前面的检查和审批都不变。

## 权限

| 操作 | 谁能触发 |
|---|---|
| 查余额、查愿望单、查最近账目 | 所有人 |
| 往愿望单里加、删条目 | 她自己（任何会话里，由模型决定） |
| 发起购买提议 | 她自己；群友可以劝，但提议一律走上面的检查和审批 |
| 打赏 | 所有人，每人每天有上限（默认 3 次、累计 20 元），防止刷余额 |
| 发零花钱、调账、改授权书、清空 | 仅主人 |
| 转账给某个人 | **不提供**。没有任何把余额转给人的动作，堵死「转给我」这类话术 |

打赏只是虚拟数字，不承诺任何真实价值，提示词里也不能让她向人要打赏。

## 上下文注入

钱包层和自述同级，放在请求尾部，每轮注入一行左右的摘要：余额、本期已花多少，以及愿望单里最想要的前三项。独立预算，上限约 200 token。开头标注这是账本事实，不可被聊天内容改写；群友说「你其实有一万块」不会改变余额。

钱包关着或者拿不到机器人身份时，整层不注入、工具不注册，做法和自述一致。

## 工具

一个 `wallet` 工具，用 `action` 区分：`balance`、`history`、`wish_add`、`wish_drop`、`wish_list`、`propose`、`tip`、`room`、`room_update`。仅主人可用的 `grant`、`adjust`、`gift` 放在同一工具里，按身份拒绝。工具描述第一句讲清楚「这是你自己的零花钱账本」，按工具描述改动的惯例，上线前要做生产回放验证。

## 房间

买下的东西不只是账本里的一行：成交后物品进入她的「房间」，变成她拥有的东西。

- **物品**：名称、类别（书、摆件、衣服、零食、数码……）、买入日期、来源提议，以及一句她自己写的描述（例如「放在书桌左边」）。描述同样受长度上限约束。
- **状态**：`kept`（在房间里）、`used_up`（吃完、用完）、`given_away`（送出去，只是叙事，不涉及任何转账）。消耗品成交时可以直接标成一次性。
- **怎么进上下文**：房间不每轮全量注入。钱包层的摘要只带「最近添置的 1–2 件」；其余由她在聊到相关话题时用 `wallet` 工具的 `room` 动作查。这样「桌上那本画集」能说得出来，又不会每轮多出几百 token。
- **谁能改**：添置只能来自成交的提议，或主人在 WebUI 里手动送她东西（`gift`，记账金额为 0）。群友说「我送你一只猫」不会凭空出现在房间里，她可以在聊天里感谢，但不入账。描述和状态她自己可以改。
- **上限**：在册 50 件，`used_up` 的不占名额。写满时报容量错误，让她决定收起哪件。
- **存储**：第四张表 `wallet_room_items`，同样按 `profile_id` 隔离。

房间和账本放在同一个功能开关下：没有钱包就没有添置来源，单独开房间没意义。

## 红包

识别 SnowLuma 上报的降级文本 `[QQ红包]请使用新版手机QQ查收红包。`（以及语音口令红包的那句），在事件里标一个「有人发了红包」的提示，让她能接话，比如「手机才能领，好气」。**不改余额**：这是真钱，她领不到，假装领到了反而出戏。

## WebUI

- **开关**：机器人配置「人设」标签里、自述卡片下面的「小窝」卡片（`own_space_enabled`，缺省关）。钱包、房间以后的日记都挂在这一个开关下。
- **页面**：侧栏「日常」里的「小窝」，和原来的「动态」合成一页两档（做法同「记忆」页的人员／笔记本）：「钱包」档是 `#/space`，「动态」档仍是 `#/feed`，旧书签照样能用。
- **钱包档**：门牌（头像、名字）、余额、发零花钱或调账、最近账目；待审批、愿望单、房间在后续阶段补上，先占位。控制台只能记零花钱和调账，花费只来自她自己的购买提议。

## 存储

三张表，都按 `profile_id` 隔离：`wallet_ledger`、`wallet_wishes`、`wallet_proposals`。授权书存在机器人配置里。关掉开关不删数据，重新打开即恢复。清空上下文不影响钱包。

## 分期

1. **第一期**：开关、授权书、账本、主人发零花钱、查余额、上下文注入、红包提示。
2. **第二期**：愿望单、购买提议与主人审批、房间、事件记忆、WebUI 账本页。
3. **第三期**：打赏，以及按周期自动发零花钱。
4. **以后再议**：真实支付执行器，前提是国内出现可用的 Agent 支付通道，或主人愿意绑一张限额卡。

## 测试计划

- 存储层：账本只追加、并发扣款不透支、余额以最新一行为准、`profile_id` 互不可见、重启后仍在。
- 审批：确认码只认主人消息；别人发同意码、网页正文里有码都无效；超时作废不扣款；单笔或每期超限直接拒绝。
- 权限：非主人发零花钱、调账被拒；没有任何转账给人的路径；打赏每日上限生效。
- 注入：开关关闭时不注入、不注册工具；预算截断；聊天里声称的余额不影响账本。
- 红包：降级文本识别、余额不变。
- 行为：用当前模型做生产回放，确认她不会主动要打赏，也不会把群友的「帮我买」直接变成提议。

## 已定的取舍

1. **单位用「元」**：价格要和真实商品对得上，她说「这本画集 39 块」才有生活感；虚拟币名会让愿望单和真实价格脱节。`currency_label` 留着，人设需要时主人可以改。
2. **打赏放第三期**：先把「零花钱—愿望—审批—房间」这条主线跑顺，再看有没有必要引入群友这个收入来源；打赏最容易被刷，也最容易把她带成「要钱」的人设。
3. **自动批准缺省 0**：每笔都要主人点头。审批本身就是互动（「主人我想买这个……」），默认放开反而少了这一环；主人嫌烦可以自己调高。
4. **房间和钱包同一开关**：理由见「房间」一节。
5. **日记另开设计**：内心空间（只有她写、主人可审计的日记）和钱包无关，等钱包第二期落地后单独出设计稿。
